# Native host terminal smoke

The host terminal uses an explicit `host-terminal` boundary. It runs the pinned Windows CMD or Windows PowerShell in the supplied host working directory. It does not use AppContainer or replace the existing sandbox terminal.

```powershell
dotnet build apps/tool-host/KYNXA.ToolHost.csproj -p:RuntimeIdentifier=win-x64
node --test tests/native-host-terminal-smoke/host-terminal.test.mjs
node --test --test-concurrency=1 tests/native-host-terminal-smoke/visible-terminal.test.mjs
dotnet run --project tests/native-host-terminal-smoke/HostTerminalDecoderSmoke.csproj
```

`KYNXA_HOST_TERMINAL_SMOKE_TOOL_HOST` may name an absolute packaged helper to test. All scripts, writable files and descendant processes belong to independent temporary fixtures. No existing user application window, user profile or project script is controlled by these checks; visible checks create and screenshot only their own console.

The native protocol accepts `host_terminal_capabilities`, or `host_terminal` with `shell`, `script`, `cwd`, and `timeoutMs`. Scripts are limited to 16,384 characters; timeouts are 100–120,000 milliseconds. CMD disables AutoRun with `/d /s /c`. PowerShell uses `-NoProfile -NonInteractive -Command`; the original script is parsed as a separate script block after UTF-8 output initialization. The source variable exists only in the child environment and is removed before executing the script.

Execution emits a `host_terminal_started` JSON line and one terminal JSON line. A normal exit, including a nonzero exit code, is `completed:true`. Cancellation, timeout and output-limit interruption after startup are `completed:false,outcome:"unknown"`; successful Job cleanup does not imply that host side effects were rolled back. The sole Job handle is not inherited, and kill-on-close covers helper termination. The Node broker must bound simultaneous helper invocations; the native Job separately limits each process tree to 32 processes.

Between startup and the final receipt, captured execution emits `host_terminal_output` with `stream:"stdout"|"stderr"`, `delta`, and an increasing shared `sequence`. Accepted complete lines use the same UTF-8/OEM decoding as the final streams; a final incomplete line is sent before the receipt. Small bursts are coalesced to bound framing overhead. The ordered frames describe observed batched output, not an exact physical ordering between concurrently written stdout/stderr. Visible mode instead emits `stream:"console",text,replace:true` screen snapshots. Execution events and final output remain available to the gateway, but the application does not render a terminal in the right sidebar. The default captured command still has no external window or interactive TTY.

The combined raw captured stdout/stderr limit is 256 KiB, reported as `maxOutputBytes` and `capturedOutputBytes`. CMD decodes each complete line as strict UTF-8 when valid and otherwise as the Windows OEM code page. This supports separate OEM builtin lines and UTF-8 child-process lines. Unmarked encodings mixed within one line, OEM byte sequences that are also valid UTF-8, binary output and arbitrary code-page changes cannot be losslessly identified. The receipt explicitly reports `outputEncoding:"utf-8-or-oem-per-line"`; it does not claim universal binary decoding. PowerShell reports `outputEncoding:"utf-8"`.

Protocol-2 capabilities additionally advertise `visibleTerminal:true`. The broker uses the distinct `host_terminal_visible` operation with `visible:true`, so an old helper rejects before executing a hidden command even if it changed between capability discovery and dispatch. It starts a bundled ToolHost companion with a real Windows console, and its pinned shell inherits console stdin/stdout/stderr. No Python or extra terminal package is required. `keepOpenMs` is optional (default 5,000; 0–30,000), only valid in visible mode, and remains inside the total timeout. A visible console window with a nonempty client area must be observed before the worker is permitted to execute the script; missing visibility never falls back to a hidden command. Windows Terminal delegation is accepted only when the uniquely titled actual host window is observed, not merely its message-only console handle.

The visible receipt reports the actual command PID, worker PID, and `windowId` with **`windowProcessId`** (the console host, which differs from the shell PID). `consoleInput:"console"` and `consoleOutput:"console"` describe real handles. `consoleText` is a latest bounded Unicode screen snapshot, not a complete stdout/stderr transcript: streams are not separated, redraws are not reconstructed, and scrolled-away rows may be missing. `consoleSnapshotAvailable`, `consoleSnapshotTruncated`, `transcriptComplete:false`, and `outputCapture:"console-screen"` make this distinction explicit. Empty `stdout`/`stderr` never means captured streams are available. Preview truncation does not kill a completed command. Visible startup requests `SW_SHOWNOACTIVATE` and places the verified own console behind the selected foreground window before executing. Its start event reports observed `backgroundPlacementConfirmed` and `foregroundPreserved`; ordinary focus restoration remains best effort and never uses a foreground-lock bypass. The console is not minimized, so explicit target screenshots remain available.

`displayHoldRequestedMs` names the configured hold; `displayHoldMs` reports the measured bounded hold. Cancellation or deadline during the hold closes the owned console but preserves an already received `commandCompleted:true` exit. While the command is running, snapshots are updated without concatenating redraws, and interruption remains `outcome:"unknown"`. The named pipe is restricted to the current user and its client PID is checked against the owned worker. Killing the helper closes its sole Job handle and kills that worker's command tree; a shared Windows Terminal host process is never killed by PID.
