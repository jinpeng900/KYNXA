- **已实现：** OpenAI Chat Completions、OpenAI Responses、Anthropic Messages 三协议文本回复与流式解析；取消向上游传递，处理断流、超时、失败和兼容服务的 JSON 回退。同聊天按稳定 ID 串行调用，已完成请求可去重重放。

## 最近一步：输出上限与真实模型能力

优先完成 C04 的独立输出上限，与确认记忆管理 UI 并行；然后配合 E 拆分列表和按需正文加载，再进入 Host/只读工具契约及后续修复闭环。C05 的完整启停、自动发现和 C07 下载放在后续 P1，不能作为 C04 或加载性能工作的阻塞项。上下文窗口表示本次输入、输出等共同受限的容量；不能把选了 1M 理解为可以输出 1M，也不能因请求预算变大自动提高所有模型的生成上限。

建议增加可选输出配置，并保留旧连接默认行为。C/E 约定预算关系，B 做简洁输入和提示：Chat Completions 使用该模型实际支持的输出字段，Responses 映射 `max_output_tokens`，Anthropic 映射 `max_tokens`；推理模型还要核对其可用输出额度是否包含推理消耗。具体参数按服务能力适配，不能对任意兼容端点强加同一种字段。

验收至少覆盖：旧连接继续可用；输入窗口与输出上限分别保存；超出服务允许的窗口/输出或预算组合时给明确错误；较长代码与报告不再被固定 2048 输出预算意外限制；超过模型上限的结束仍记为未完成，保留已有内容，不静默重新生成。原始聊天日志、确认记忆、来源和稳定 ID 不因调整预算而改变。

模型元数据应区分“服务确认”“官方规格”“用户手动配置”“未知”。官方规格与实际部署参数可能不同：本地启动的上下文也要匹配推理服务实际设置；不能只保存一个更大的客户端数字。服务不提供能力查询时允许明确的手动配置，并说明无法自动验证。云端真实窗口与可用额度、本地大窗口的内存和延迟需分别测量，不能以合成测试替代。

## 本地模型和下载需求如何落地

第一轮支持选择已有推理服务或已有模型文件。配置文件位置不等于模型权重位置；直接 API 模式只连接服务，只有选择“由 KYNXA 管理本地服务”才由应用负责进程生命周期。启动后以健康检查和模型 ID 确认就绪，不能仅凭进程存在显示成功。

上述“由 KYNXA 管理本地服务”是 C05 的待实现选择，当前界面没有这一完整生命周期入口。现阶段先启动推理服务，再配置连接；软件启动自动打开网关，不会自动加载用户模型。普通用户安装 Ollama 后自动列出模型、可选启动其服务、拉取新模型后刷新列表属于后续 P1，而非当前手动“获取模型”按钮已经完成的自动发现。

C05 验收分两条路径：

- **已有服务：** 读取真实服务返回的模型 ID，能刷新新增/移除模型；服务离线、未加载模型、需要认证或地址错误时状态明确，不依赖某台电脑已有的 Qwen 路径。Ollama 动态发现与直接 API 的显式地址分别验证；不把探测其他接口当成模型已可生成。
- **应用管理的服务：** 用户明确选择后才启动；记录引擎、权重、参数、端口及进程所有权；健康检查与模型 ID 验证成功才显示就绪。测试端口占用、文件缺失、加载失败、显存不足、启动取消、重启与关闭策略；只停止本应用创建并确认归属的进程。
- **资源与配置：** 空闲服务内存和模型加载/生成时内存分开测；并发打开应用不重复加载模型；本地实际上下文与连接配置不一致有提示。关闭应用是否保留用户自行运行的服务与是否关闭本应用管理的服务分别按约定验证。

C07 与 B/D 合作：B 做页面，C 做下载与运行时适配，D 管文件范围和外部资源校验。首批选择明确格式和运行时组合，例如已验证的 GGUF 与 llama.cpp；不能承诺任意下载的权重都可直接加载。记录来源、模型版本、大小、哈希及适用运行时，下载到临时文件、校验后完成安装，失败不留下“已安装”状态。

预设已有多家服务商；先修完善的模型选择、能力描述和诊断，不以增加名称数量代替完成接入。实施时再核对供应商官方文档的模型 ID、协议与限制，本计划不承诺某一型号永久可用。
