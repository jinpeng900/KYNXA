# C：模型接入与本地推理

[总览](队长总览.md) · [分工入口](README.md)

**你的成果：云端和本地模型都能稳定调用，能流式回复、取消，并向 Host 返回明确的工具意图。** 保留直接连接本地 API 和经过 Ollama 两条路径。

## 接手位置与边界

- `apps/model-gateway/server.mjs`、`runtime.mjs`、`protocols.mjs`、本地启动脚本和网关测试。
- 提供 `ModelPresets.cs` 的模型元数据；B 负责模型管理窗口。与 E 配合迁移 `store.mjs` 的会话持久化，与 D 配合替换凭据存储。
- 网关不执行工具、不批准文件修改、不自行维护第二套 Work 状态机。

## 本地模型和下载需求如何落地

第一轮支持选择已有推理服务或已有模型文件。配置文件位置不等于模型权重位置；直接 API 模式只连接服务，只有选择“由 KYNXA 管理本地服务”才由应用负责进程生命周期。启动后以健康检查和模型 ID 确认就绪，不能仅凭进程存在显示成功。

C07 与 B/D 合作：B 做页面，C 做下载与运行时适配，D 管文件范围和外部资源校验。首批选择明确格式和运行时组合，例如已验证的 GGUF 与 llama.cpp；不能承诺任意下载的权重都可直接加载。记录来源、模型版本、大小、哈希及适用运行时，下载到临时文件、校验后完成安装，失败不留下“已安装”状态。

预设已有多家服务商；先修完善的模型选择、能力描述和诊断，不以增加名称数量代替完成接入。实施时再核对供应商官方文档的模型 ID、协议与限制，本计划不承诺某一型号永久可用。

## 第一周与验收证据

第一天跑现有网关测试并整理接口；第二天与 A 定增量事件；第三天提供模拟流与工具意图；第四天接一个真实模型流；第五天与 B 演示停止和断流。

交付协议测试、真实调用记录、本地启停说明、模型/硬件/上下文配置和耗时。固定模型替身证明协议行为，真实服务证明实际接入，两类结果分别报告。不要把真实密钥或用户会话提交到测试样本。
