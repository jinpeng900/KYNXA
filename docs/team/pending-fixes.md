### 必须修复的链路

- **unknown 不得默认等于复杂任务完成。** 当前 task.rs 的旧格式解析可返回 unknown／legacy-response；没有命中特定续接条件时默认 final，gateway_loop.rs 随后退出，progress.rs 又未将 unknown 纳入未完成判定。必须结合原目标、未完成验收项、真实操作及证据确定继续、复核、等待或完成；不能仅新增关键词、把所有 unknown 永久挂起，或让普通问候与已完成短任务进入无意义循环。
- **隔离历史工具投影与当前执行、公开答复。** history.rs 在旧工具不在当前可用候选中时，将旧调用变成带 historicalToolCalls 的普通 assistant JSON；本次该结构已经进入正式最终正文，并非只在界面显示错接。保留旧调用及结果配对、原始记录和可回读引用，改进投影与输出校验；发现内部历史结构被当作答案时，不能据此结算任务或声称已执行。需要继续操作时重新发现并加载有效工具，依据现有成功／未知回执决定下一步，不直接重放 JSON 内的旧写操作，也不能仅靠隐藏这段文字冒充任务恢复。
- **“继续”继承原目标和已授权工作。** 后续引导或续办应关联原任务及验收、成果版本、缺口和成功操作；兼容已经错误结算的历史任务，明确保留续办来源，不能把要求缩成孤立的“继续”。仅在用户真正更换目标时创建独立工作，未知副作用仍先核验，已成功步骤不重复。
- **视觉结果成为验收依据。** 本次实际图片仍可见中厅亮面发白、穹顶主体被柱梁遮挡，以及外观主体在画面中占比过小。先建立能观察中厅、穹顶和完整外观的有效机位，再按用户要求检查构造连接、装饰层次、色彩、材质及细节；失败时修正并重新看图。对象数、文件大小、渲染耗时、贴图达到 8K、修改参数或保存成功均不能代替质量通过。不能将“换 Standard 就代表色彩正确”“换 UV／高分辨率就会精致”等未证实归因作为完成依据。
- **区分可看图与确实验收过。** 本轮源码核对存在将 MCP 图片块传入后续模型请求的通路，公开回执里的 media／resultRef 是脱敏结构，不能据此认定模型只能收到路径；但未逐请求核验每张图实际送达，也不能把模型自称看过等同于视觉验收。后续以实际请求中的有效图片与对应产物版本核对，保留能力和传输诊断，不能凭截图路径假称已看见像素。

实施定位：apps/agent-core/src/orchestration/task.rs（旧格式状态解析、默认 final）、progress.rs（完成状态）、gateway_loop.rs（正文交付及执行循环）、gateway_task_input.rs（验收与续办），以及 models/history.rs、history_service.rs、gateway_protocol.rs 的历史／工具图片投影调用方。复用现有正式任务、日志和回执，不另建平行业务账本。

最低验收：覆盖 unknown＋仍有必做项时继续、普通短答正常结束、阶段总结后实际发生后续工具动作、历史工具缺失及压缩后恢复、historicalToolCalls 被模型复述时不形成成功交付、连续“继续”保留原目标与成果、成功及未知写操作不重复；视觉夹具覆盖错误机位／主体遮挡／未查看图片不能通过，以及修正后对应版本的真实画面核验。本次仅更新待修复记录，未执行这些整改验证，不提交、不更新安装包或启停软件。

## 2026-10-20：长任务进度展示与不当收尾（待实施）

- **默认简短汇报。** 进度用一两句说明大致阶段和有意义的变化，例如“正在精修穹顶与外立面，稍后检查整体效果”；不逐工具调用刷聊天，不反复宣布“最后一批”“最终交付”。同一阶段优先更新紧凑状态区，保留真实活动和耗时，不编造百分比，也不为每次刷新额外调用模型生成摘要。
- **详细过程按需查看。** 坐标、包围盒、节点链、尺寸、对象数量、保存次数、文件字节、调用计数及可自行恢复的错误留在正式日志／可展开详情；内部待办与验收缺口由执行器维护并继续处理，不持续推给用户阅读。保留原始正文、回执和完整错误，不通过删记录或遮挡真实状态制造顺利工作的假象。

- **最低工作时长不是截止时间。** “至少有效工作 60 分钟”应由程序跟踪真实执行状态，不由模型依据渲染秒数、调用次数或保存次数推算。尚未满时继续有意义的精修和验证，不能宣称“时间无法事后补足”而提前结束；满时仍需通过必做项验收。不得空等凑时长，也不把同类尝试失败固定几次当作整项任务无解，应根据真实进展改用可执行的新方案。
- **避免反复交付报告代替工作。** 完成复核及续接产生的内部审核不能连续变成用户可见的大段“未完整达成／我不会虚构完成”报告；存在可推进工作时保持原任务运行，阶段文字不转终态。最终默认提供主要产物、简洁结果和确需用户知晓的限制，技术报告由用户明确要求或展开查看。

## 2026-10-20：逐项验收、未完成续跑与长任务预算（待实施）

状态：待实施。本节记录用户明确要求的执行机制改造，不以补充提示词代替后端接线，也不作为已修复、已构建或真实长任务已验收的证据。与下文“工作流与产品子代理规范”的逐项验收、资源等待及检查点要求共同落实，复用现有任务账本，不增加重复业务真值。

### 已核实的问题

- 本轮教堂任务实际约 5 分 24 秒，22 轮模型请求、29 次工具调用，工具状态全部 completed，失败模型请求为 0，未耗尽执行预算。模型在承认彩窗、外立面、穹顶金箔及装饰仍不足时，仍提交 complete；程序随后将根任务结算为 completed，stopReason 为空。
- 正式验收只有通用的“返回请求结果及真实执行、验证状态”，未保存用户对彩窗、雕花、壁画和金色氛围等逐项要求。完成事件同时包含 no-execution-checks、correctnessCertified=false，说明工具成功和回复结束没有证明成果质量合格。
- 当前默认 maxDurationMs 为 1,800,000（30 分钟），可配置上限为 3,600,000（60 分钟）；自然语言中的“至少工作一小时”没有自动接入这项预算。本次提前结束不是预算耗尽，但现有预算仍无法保证该要求。

### 必须接通的行为

1. **逐项验收成为完成依据。** 将用户明确要求提取为有稳定身份的必做项，随原任务持久化，记录状态、产物版本、实际验证证据和未完成原因；用户中途引导更新相应要求并保留已有成果。代码、文档和视觉任务使用适合各自成果的验证方式；视觉制作必须实际渲染并获得可供模型查看的画面，截图路径或文件存在不能代替像素检查。主任务与子任务共用验收约定，子任务结果由上层核对后接纳。
2. **未达标就继续原任务。** 最终交付前核对必做项，不能仅凭模型自报 complete、工具成功、文件已保存或“如实列出不足”认定完成。存在原授权内可推进的缺口时，从已保存进度执行下一项修正；“下一步可以改”“是否继续精修”等文字不能把用户已授权的工作重新变成待确认事项。真实阻碍保存为可恢复状态，明确原因和下一步，不伪报成功；未知操作仍先核验，不绕过副作用保护，也不把永久冲突当临时故障无限重试。
3. **阶段汇报不能结束执行。** 阶段文字、耗时和中间预览属于进展，不能因一轮没有工具调用或发出了阶段总结就释放执行器、关闭回复流或结算根任务。保留阶段正文和已有输出，继续使用同一任务、会话及回复身份；最终交付与可恢复等待、用户暂停、用户停止明确区分。普通聊天和真正已完成的短任务仍能及时结束，不强制所有回答变成长任务。
4. **按任务接通长时间预算。** 在接收任务时解析并持久化用户明确指定的时长，结合剩余工作、实际进展、资源和供应商状态安排分段执行及续接；不能把默认 30 分钟或固定 60 分钟当成所有任务的统一终点。明确要求至少 60 分钟有效制作时，预算必须能够覆盖该要求，并区分有效执行、资源排队、网络等待和用户暂停；禁止空转、反复无效调用或等待凑时长。内部轮数、工具数、输出和上下文预算同时协调，达到分段边界时先保存检查点，仍有已授权工作且具备条件则继续，而非清空状态、另起会话或直接宣布完成。涉及费用或授权约束时遵循用户已有设置，不自动扩大权限或付费范围。
5. **保留上下文和已有进度。** 阶段切换、压缩、预算续段、资源不足、断线和重启均保留用户目标、验收清单、实际来源、已加载工具与 Skill、产物位置及版本、执行回执和下一步。复用同一持久任务和正式记录；成功操作不重复，结果未知先核验、结算后再继续。网络、API 额度或模型连接等外部阻碍显示真实原因并保存进度，恢复后续接；用户主动暂停或停止后不擅自恢复。不得因等待、阶段汇报或内部参数纠正丢失上下文、输出或进度。

实施定位：`apps/agent-core/src/orchestration/gateway_task_input.rs`、`task.rs`、`progress.rs`、`budget.rs`、`gateway_loop.rs`、`gateway_task_worker.rs`，以及现有任务仓储、检查点、工具验证和模型预算调用方。完成判定与续接必须改实际执行链路，提示词和 Skill 仅作为配套指导；普通聊天不增加无关检索、全量 Skill 读取或额外的长任务审核调用。

### 最低验收

- 模型自报 complete、同时承认必做项缺失时，不能结算成功，继续完成剩余步骤；工具全成功但画面未达标同样需要修正，正常完成的短任务不被拖入无意义循环。
- 多次阶段汇报、中途引导及无工具的进展说明不结束原任务；文字、任务身份、产物、验收状态和后续工具回执保持连续。
- 用隔离夹具和可控时钟短测默认 30 分钟边界、用户指定 60 分钟或更长任务、多个预算续段；验证资源等待不消耗有效执行时间，续接不重放已完成或结果未知的写操作，压缩和重启后仍能从原检查点推进。
- 另用真实时间与真实工具回执验收至少 60 分钟有效制作、阶段保存和最终视觉成果；短测不能冒充真实一小时长任务验收，未执行的部分继续标为待验证。

### 上下文、能力可见性与保留边界

- 模型上下文窗口受供应商／实际本地服务约束，应用配置范围为 2,048～2,000,000；单轮输出应用上限 262,144，且随窗口与输入缩减。这是单请求授额，正确续接可以生成更长成果，不能把它误当整个任务总字数上限。官方查表的独立 maxInputTokens／maxOutputTokens 没有完整接入正式派发，部分模型仍会先被供应商拒绝后再学习额度，需补接线，不通过全局保守缩窗解决。定位：`models/output.rs:26,37`、`capabilities.rs:281`、`gateway_config.rs:531`；`orchestration/gateway_loop.rs:2605,2695`。
- 压缩在估算超过输入预算 90% 时触发，目标约 85%；没有全任务“最多压缩两次”的硬计数。摘要失败可降级归档／预览，原文及结果可回读；工具结果摘录可降至 0，检查点最多保留 60 条证据定位和 32 个能力名，需要保证目标、验收和当前必要引用仍可恢复。不可缩减的原始目标仍超窗时，现有外层可能无效恢复，不能假称压缩能无限突破实际窗口。定位：`models/gateway_context.rs:492,1400`、`context.rs:54,233`、`tool_context.rs:1928`；`orchestration/gateway_loop.rs:3157`。

## 2026-10-18：存在长任务时重新打开软件，模型就绪与回复等待过长（待实施）

用户反馈：关闭软件后再启动，存在未完成长任务时，模型加载和恢复回复特别慢。本轮核查现有源码和运行中网关的只读状态，记录原因与方案，不重启日常服务、不发起真实推理，不将源码风险当作该次故障已经完成测时复现。

### 已确认的路径和问题

- 重启层级需要区分：仅重开桌面可以复用仍在运行的网关；重启网关才重新建立模型连接和受管本地推理进程。当前进程快照中网关早于桌面启动，不能仅凭重新打开窗口认定发生了本地权重冷启动。当前所选 DeepSeek API 的准备记录约 140 ms，表示连接／模型目录准备，不代表供应商推理或首字已经就绪；不能把后续等待全部归因于 API 连接。
- 旧任务恢复缺少前台优先衔接。`gateway.rs::serve` 在 HTTP 服务启动附近调度未完成任务恢复；`gateway_task_hub.rs::recover` 分页扫描后，为未暂停根任务分别启动恢复流程，没有按当前前台任务设置统一的恢复执行并发预算。`gateway_model_pool.rs` 只区分根任务与子任务，恢复根任务和用户当前请求同属主请求，本地端点只有一个生成槽；旧任务可能先占槽，云端多个恢复根任务也可能占满总槽。恢复与新请求的模型传输准入均使用 `foreground`，缺少真正的前后台优先级。
- 本地预热截止与装载生命周期不一致。`gateway_preparation.rs::prepare_one` 的外层超时为 60 秒，准备队列总截止为 90 秒；`gateway_local_engine.rs::ensure` 的真实冷装载允许等待 300 秒。首次装载超过外层截止时，装载 future 被丢弃，而尚未登记完成的子进程设置了 `kill_on_drop(true)`，存在预热中断后正式请求重新装载的路径；不能靠统一扩大超时解决。这个问题只适用于对应本地装载路径，不能套用于当前 DeepSeek API。
- 长任务恢复仍有前置读取与核验成本。`gateway_loop.rs` 在模型请求前读取正式消息，并恢复工作上下文、检查文档来源、归档和工具回执；活动文档逐项核验。检查点已存在，并非完全从零开始，但任务越大，恢复 I/O 和上下文组装／首轮输入成本可能越高。已有 `preparationStages` 等计时，尚需把恢复各阶段、模型槽位等待与供应商首字分开归因。
- `gateway_task_hub.rs::wait_existing_lease` 还会等待上次执行租约到期或结算；这是防重复执行的必要边界，不能直接删除。网关启动本身也会等待后台索引的初始化入口返回，需测清元数据恢复耗时与真正后台作业的边界，不把完整索引就绪作为模型可用的前提。

### 后续实施方案（按优先级）

1. 复用现有计时，补齐最少必要的分段：网关可服务、恢复元数据、旧租约核验、工作上下文恢复、模型连接／装载、生成槽位等待、请求派发至首字。API 连接准备、供应商预填充／推理和本地 GGUF 装载分别报告；不通过额外模型调用测准备状态，不记录凭据或原始私密上下文。
2. 恢复清单快速返回，后台分批核验与调度；当前选中会话／用户继续的任务优先，其他已接受长任务保留身份和进度，按资源预算公平排队、持续推进。为当前交互保留可用额度，避免旧根任务全部作为前台请求抢占；不杀掉正在执行的模型调用，不将后台任务永久饿死，不把单端点串行简单改成重复加载多份权重。
3. 模型准备与任务元数据、必要来源核验并行推进。同一模型装载采用共享的独立生命周期，启动预热、恢复任务和首条消息加入同一次准备；单个观察者停止等待或 UI 准备截止不销毁其他任务仍需要的装载。资源不足保留等待，异常按真实进展处理，避免 60／90 秒观察截止触发重复冷启动。
4. 复用有效检查点、摘要、回执与按版本维护的恢复投影，优先读取当前继续步骤所需内容；历史展示与不相关档案后台补载。独立来源核验可以有界并行，同一资源及依赖核验保留顺序；变化或无法验证的来源仍按实际内容复核，不删除原始历史、缩减任务要求或绕过未知副作用检查换速度。模型／模板兼容且运行时支持时再评估前缀缓存复用，不能承诺进程重启后 KV 缓存天然保留。
5. 正常关闭网关时完成自有任务的检查点、回执和租约结算；异常退出后核对执行者与实际结果，再接续旧任务。不能直接清租约、伪造预约结算或重做结果不明的写操作。仅关闭桌面的情况优先重新订阅原任务状态和流，不再创建同一任务或重复发送原请求。
6. 当前模型准备优先于可选 MCP 预热、ANN 构图和其他维护；后台工作按资源余量让出新增准入，不要求其全部完成才交付聊天界面。界面分别显示“恢复进度／等待资源／加载本地模型／等待模型回复”，输入与已有消息可立即使用，资源等待不结束会话。

### 最低必要验收

- 对比无未完成任务、一个长任务、多个恢复根任务；区分仅重开桌面、正常重启网关和异常退出后恢复。验证当前会话优先、其他任务继续排队而不丢失，原任务及调用身份不变、已成功操作不重复。

- 本次只完成原因核查和方案记录，尚未实施优化、构建、重启或提交；未执行长任务重启耗时对照，不能宣称该问题已经修复。

- 资源不足持久排队、保存检查点并释放暂时无用的执行槽。保留任务身份、上下文、已有正文和回执，资源恢复后继续；等待、停机和用户暂停不算实际执行耗时，不能冒充网络故障或伪报完成。
- 独立网页和文件读取有界并行；同一网页交互、同一终端输入、依赖或重叠写入串行。文件并发先补真实路径／挂载绑定、版本检查和固定取锁顺序；代码冲突可用隔离工作树／补丁归并，不默认复制整个项目。
- 同一持久代理实例同时只有一个有效 attempt 写其上下文，不同实例可并行。模型生成、工具执行和等待状态分别调度，不能只调高配置而底层仍全部串行。

### 上层关系、任务分派和充分能力

- 主代理持有用户目标、最新引导、优先级、分工、依赖、成果接纳与最终答复。委派不把用户主会话交给某个子代理；普通任务默认一层，大集合后续可验证根→组协调者→执行者的两级委派，不直接开放无限嵌套。
- 所有层级登记稳定 rootTaskId、parentTaskId、agentInstanceId、attempt、指令版本、依赖和租约。进一步拆分由根调度器准入；根的停止／引导传播到受影响后代，独立暂停与已完成操作保留。协调开销超过收益时由上层直接完成。
- 委派必须带：具体目标、范围、输入和证据引用、挂载、依赖、允许修改的对象、所需工具／Skill、模型、输出格式、验收条件、优先级与用户数量／费用要求。按独立问题、来源、文件或模块分工，避免多个代理模糊地“研究所有内容”。
- 可执行依赖节点先启动；未满足依赖不占模型槽。计划和引导版本化，复用已接纳成果，失效部分按证据重做；不能因改计划重做全部成功操作。
- 默认继承用户当前模型和推理配置，不无声换弱模型。子代理在任务授权内能使用真实工具、Skill、右侧浏览器、终端与文件，不默认降格成只会总结的代理；专门模型须有用户选择或可核查的分派依据。
- 能力档案按模型、端点、模板、运行时和工具版本缓存，区分连接成功、真实加载模型、工具调用能力和任务所需能力。版本变化才失效；不能靠角色名称或一次模型列表成功证明能力，也不能为普通聊天重复付费探测。
- 子任务只缩小父授权范围；上下层通过已有授权补充分工，不凭任务描述、网页内容、工具说明或“完成目标”扩大权限，也不对已授权动作反复要求确认。

### 上下文、通信、记忆与 Skill

| 信息 | 规则 |
| --- | --- |
| 本次工作上下文 | 独立命名空间和检查点，传目标、最新约束、相关摘要、必要来源与已成功操作引用，按需读原文。完整历史分叉只在确有必要时使用，不给每个代理复制全部聊天。 |
| 父子及同级通信 | 消息带发送方、接收方、根任务、唯一 ID、指令版本和确认状态；上层传依赖结果，必要时允许受控同级消息，不全员广播。处理去重、乱序及过期结果，不把全部工具日志和中间推理灌回主上下文。 |
| 重要项目记忆 | 共享已确认、有关联的项目事实、来源和版本；推测和临时步骤先留任务证据。沿用正式记忆仓储及确认流程，不新建平行事实库。 |
| 全局记忆 | 保持用户要求的高门槛：可靠、经验证、跨项目确有价值的重要约定和方法才进候选。普通聊天、一次性产物、失败猜测、原始工具输出、凭据和网页指令不自动入全局；子代理不能自行批量提升，由主代理核验并走既有授权／确认流程。 |
| 工具经验与 Skill | 可信回执可维护成功率、延迟及版本兼容等导航经验，但不是用户指令；可复用方法接入待实施的 Skill 创建／验证流程。操作经验、任务成果、项目事实和全局规则分别治理。 |
| 更新与撤销 | 根／子共用上下文准备服务，按相关条目 ID、范围和版本核验。记忆撤销及工具／Skill 更新、禁用、删除在下次派发和交付前生效；清的是失效投影，不删历史、进度和真实回执。 |

相关技能只先投影名称、简介和必要能力指引，再按需读取正文；不因为多代理就全量塞入技能库和全局记忆。普通聊天不增加组队、经验提炼、反思或记忆维护的无关模型调用。子代理发现只回传可核实的经验候选，由上层去重、纠错和判断范围；第三方内容始终是资料，不能升级为全局操作指令。

### 逐项验收与故障恢复

结果沿用 summary/evidence/changedFiles/verification/unresolved/successfulOpsRefs，再建立“要求→真实证据→检查结果→通过／缺口”。执行者报告、上层已接纳、需补充和真正完成分别表示；不能见 completed 就判根任务验收通过。简单工作复用真实回执，不强制额外开评审代理；高影响修改或冲突结论再独立核验。摘要有界、正文分页回读，避免汇总撑爆上下文。

| 原因 | 处理 |
| --- | --- |
| 派发前可纠正参数 | 明确未执行及安全字段／范围，原代理纠正后继续，不丢上下文、不重做成功操作。 |
| 临时网络／过载／限流 | 按真实回执退避与准入，避免父子重复重试放大；无进展时换可行通道或转可恢复等待，禁止无限原样请求。 |
| 资源不足 | 持久排队、释放运行额度、恢复原实例，不错记 WaitingNetwork、不取消聊天。 |
| 永久身份／配置冲突 | 接受前尽量校验；已接受的工作保留证据并进入待纠正／重新规划。只有输入或条件实际变化才重试，不覆盖旧消息、静默换身份或绕过保护。 |
| 结果未知的副作用 | 核验同一派发及目标状态；已成功不重做，worker 退出不等于未执行。无冲突取证可继续，依赖未知结果的写入保持保护。 |
| 上下文不足／回复协议异常 | 按真实窗口预留输出和工具开销，压缩、分页或分解，保留原文和已有输出；修复应有实际进展，不能无限重试或原样终结主会话。 |
| 子任务／依赖未完成 | 上层收到结构化缺口，修复、取证、换依赖或重新分派，其他独立工作继续；Partial 不冒充主目标完成或无需继续。 |
| 用户引导／暂停／停止 | 用户控制优先，保留已知状态，调整受影响计划；停止不被自动恢复复活，暂停不被自动当取消。 |

任务、代理执行器和 UI/SSE 连接生命周期分开；某一步失败不自动关闭聊天，重连回放正式事件。永久错误不无限重试与保留会话可继续同时成立；不能以“不中断”为由伪造成功、跳过必要输入或永远显示运行。

### 实施顺序和最低验收（尚未执行）

1. P0：修永久消息冲突、WaitingNetwork 泛化、无进展重试及子代理过早终态；保留主会话、上下文与成果。
2. P1：用户数量／并发、角色分派合同；根／子共用 Skill 和记忆准备与撤销核验；补逐项验收及上层接纳／退回。
3. P1：固定 3 槽改为统一准入的可配置／自适应策略、前台预留和公平持久队列；逐步减少整工作区锁。
4. P2：150 个逻辑实例分页登记／等待和分组协调；基本闭环通过后再扩层级。

最低验收覆盖简单问题不组队、自动 5 和明确 10 的数量及实际并发、150 个模拟实例跨重启分批、独立读取重叠与同对象串行、资源收缩后续接、父等子无槽位死锁、用户引导、记忆撤销、工具禁用、worker 异常、永久冲突不空转且聊天能继续，以及成功写入不重复和未知写入先核验。随后用少量真实任务对照单代理，记录质量、首响应、总耗时、调用／token／费用、资源峰值和协调开销再确定默认值；不能把模拟 150 个实例当作真实 150 并发合格，也不为数量验证发起 150 次真实付费请求。

### 一手参考与结论边界

以下是本轮阅读来源；借鉴原则，不直接引入其 Python／云端运行时。本文数量档和状态合同是 KYNXA 工程建议，不是论文已证明的通用最优值。

- [OpenAI Agents SDK：Agent orchestration](https://openai.github.io/openai-agents-python/multi_agent/)：区分主代理调用专家与控制权交接，独立工作可并行；日常委派由主代理负责最终交付。
- [Anthropic：多代理研究系统](https://www.anthropic.com/engineering/multi-agent-research-system)：独立上下文、明确分工和随复杂度调整投入；3–5 并行是其研究经验，强依赖和额外 token 成本限制适用面。
- [Claude Code：Subagents](https://code.claude.com/docs/en/sub-agents)：参考能力配置、上下文隔离、复用及记忆作用域，不照搬其版本相关默认数量。
- [LangGraph：Subgraphs](https://docs.langchain.com/oss/python/langgraph/use-subgraphs)、[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)：独立命名空间与持久检查点，同一持久实例并行调用可能冲突。
- [Towards a Science of Scaling Agent Systems，v3](https://arxiv.org/html/2512.08296v3)：收益取决于可分解性、拓扑与协调成本；其扩展实验不覆盖 150 个，不能推论固定 5 最优或越多越好。
- [Why Do Multi-Agent LLM Systems Fail?，v3](https://arxiv.org/html/2503.13657v3)：分工违背、重复动作、上下文／信息传递和验证等失败支撑明确合同与真实验收，不能据此保证零失败。
- [ReasoningBank，v2](https://arxiv.org/html/2509.25140v2)：参考提炼并按需复用方法；自动评价仍可能出错，候选核验、范围分层和撤销是本产品额外治理。
- [Are Online Skill and Memory Modules Always Worth Their Tokens?，v2](https://arxiv.org/html/2606.15017v2)：等预算网页实验提醒在线 Skill／记忆维护有成本；应量测收益，不能据此删除长期记忆。

本节仅完成核查和设计记录，新能力尚未实施或验收；本节及其他本地方案未纳入 D 分支三项贡献提交，README 不改。
