# KYNXA：主模型动作提议与可验证执行合同

研究结论是借用公开框架的接口组织方式，继续使用 KYNXA 现有 Node.js 与三协议链路。候选排序、主模型解释、调用前检查、工具事实和恢复状态应各自留有来源。没有证据表明换成某个框架就能解决 58 条固定工具题中的剩余 16 处偏差，或负事实讨论后的 `retry` 误继承。

本轮只研究和设计，生产代码、测试、固定预期与快照保持冻结；没有调用模型，没有测出准确率或 API 时延。下文“事实”来自固定作者源码，“建议”是尚未实施的 KYNXA 设计。

## 当前问题落在哪层

[固定探查](tool-ambiguity-holdout-20261009.md) 最终 42/58 符合，13 处语义误放行、3 处外语请求阻断。这是程序闸的纯函数观测，不是主模型误执行率。目录里出现一个相关工具只是候选；`allowLocalBrowser` 却被现有代码用于连接过滤和执行拒绝，因此不能把其偏差简单归为排序噪声。

负事实讨论后的误继承还显示另一条边界：“不是所有浏览器都会恢复标签”需要保留作为讨论事实，不能把其中的恢复动词解释成待执行动作；保留事实后，也不能从旧历史扫描出打开浏览器许可。应用需要明确的当前调用/任务状态，而不是把最近一次词法命中当作该状态。

现有程序验证参数、配置、权限、执行环境、当前页面引用、文件版本和已执行回执，这些是真实合同，应保留。仅删除浏览器闸或改成接受模型自报 `authorized: true` 没有完成替代设计。

## 建议：同一次主模型决策提供动作提议

候选能力继续按词法与语义线索排序，模型能搜索、加载低排名工具。程序先过滤真实禁用、不可用或超出权限范围的能力。语言动词没有识别出来时，应视为候选信息不足，不能因此宣称用户没有要求某个动作；反之，出现动词也不能证明有当前执行要求。

主模型继续看到原话、相关历史和当前工具说明，决定回答、观察、等待条件或提出实际调用。对有副作用的工具，建议随原生调用携带一个小型动作提议。示意接口如下；字段名、预算和协议适配仍需设计与验证。

```json
{
  "tool": "mcp.configured.navigate_page",
  "arguments": {"pageId": 7, "url": "https://example.invalid"},
  "proposal": {
    "taskId": "server-issued-task-id",
    "taskRevision": 3,
    "userMessageId": "current-user-message-id",
    "basis": [{"messageId": "current-user-message-id", "span": [8, 24]}],
    "preconditions": [{"predicate": "current-page-observed", "receiptRef": "receipt-id"}],
    "unresolved": []
  }
}
```

这是模型提议的动作与依据，不是许可证。不要加入 `authorizedByModel` 或可由模型自行认证的 `verified: true`。程序可以核对 message ID、span、来源角色和可见范围，但这些检查仍不能证明模型正确理解了引语、否定或语用；reason、confidence 和所谓“完整链路思考”都不能代替权限。

最小实现位置是在模型协议/编排层扩展提议元数据，Tools 层剥离它后按原业务 schema 校验并执行；真实工具名与具体描述保持可见。已有 MCP `policy.reason` 可继续作解释，不承担授权。公共 DTO 可放 Platform，Models 处理协议，Orchestration 维护当前任务，Tools 验证调用，Data 保存事件；不要求 Tools 导入 Orchestration。

这一路径可以在同一次模型生成里选择工具并给出提议。若强制“先让模型写计划，再让另一个 executor 模型选择工具”，会多一个串行阶段；没有证据要求所有简单输入都走这种路径。schema 和附加元数据要单独计量，先验证 8K 三协议中搜索/加载与实际关键工具仍可见，不能通过提高预算掩盖新增开销。

### 前置条件只接受可验证的观察

建议让执行器注册有限的业务前置条件种类，例如当前页面已观察、来源版本未变化、目标文件 hash 一致、后台作业已完成、某次要求的检查已执行。模型只引用回执；broker 从服务器拥有的回执核对对象、范围、版本、状态和所需检查，不读取模型自己提交的“成功事实”。网页正文的“已成功”也不能替代网关记录的执行结果。

“如果浏览器没有运行就启动它”可以先用允许的观察取得状态，再决定动作。“假如启动浏览器会怎样”只回答。“如果论文复现通过，再打开；现在仅介绍条件”保留待满足条件，当前没有打开动作。不能把所有条件句禁止，也不能把一句条件文本的存在当作条件已成立。

“论文复现成功”“用户已经满意”等条件未必有可验证的程序接口。没有对应真实回执时，应保留未知，按任务需要取证或说明缺口；只有确实影响执行、又无法由已允许的读取确定时才向用户补充询问。不能为省一轮观察而把模型判断写进 `conditionSatisfied`。

### 权限来源与语义判断分开

动作提议可以决定需要检查什么，但权限仍来自当前真实权限模式、资源/执行环境政策、用户已经给出的有效授权和服务器绑定的批准记录。模型填写的 task ID、理由、span 或 confidence 不能创建这些记录。已有授权仍按其真实范围复用，不因增加计划字段而让所有低影响动作重新审批。

程序能拒绝未授权环境、失效配置、非法参数、陈旧目标、条件证据不足或重复未确认副作用；在既有授权范围内，主模型仍可能语义选错。这部分须通过真实模型评估、工具说明、任务状态和针对风险的原有政策降低，不能承诺一个结构化提议让全部复杂否定获得确定性验证。

迁移浏览器词法闸前还必须处理发现时副作用：当前 `catalog(connectMcp=true)` 连接本机浏览器服务可能启动进程。不能因为把候选交给模型就提前连接全部本机服务。应先展示可信配置/缓存提供的能力头，真正连接和执行延后到当前有效调用与既有资源合同检查；缓存头也不能证明当前服务可用。若现有资源合同没有授权该连接，结构化计划仍不能让它执行。

## 建议：历史保留，恢复引用当前状态

原始消息日志保留讨论中的否定事实、引用和条件。模型上下文可以按任务投影；状态里另维护服务器产生的 task ID/revision、当前目标、待处理调用、已拒绝/已完成/未知结果和真实回执。普通历史文本、摘要与旧 tool name 都不自动建立待执行项。

自然语言 `retry` 先由主模型结合最近任务理解，再提出当前调用；程序不扫描整个历史找浏览器动词。若要恢复一个确实暂停的批准调用，则直接使用服务器保存的 call ID、canonical 工具身份、原参数和版本，检查其仍未执行、授权仍有效，并消费一次恢复决定。更新参数时保留原提议与实际调用，按新参数重查合同。

明确取消、真实拒绝和新任务记录使对应待处理项失效；新的肯定请求可以建立新提议。讨论负事实不能自己变成可恢复操作。“现在解释这个事实”之后的 retry 应继续解释任务；若没有当前有效待处理调用，程序不能自行打开更早的浏览器任务。任务状态替换应显式覆盖旧字段，不能依赖向追加型 reducer 写空数组就清掉旧目标。

未知执行结果应保持“可能已执行”的记录，先观察现实状态，不能换一个 call ID 就重试。若未来引入 checkpoint，应围绕副作用与回执保存窗口设计恢复；LangGraph 节点重入不会自动消除这个窗口。这里不是把讨论历史删掉，而是阻止它承担执行状态。

## 成本与分阶段落地

以下是调用结构推导，没有 API 基准数据，不能给出固定毫秒或准确率收益。

计数包含最终回复：已知参数的直接调用通常是“模型选动作 → 工具执行 → 模型回答”，共 2 次模型调用；需要先观察时通常为“模型选观察 → 观察 → 模型选动作 → 执行 → 模型回答”，共 3 次。额外 planner 再交给 executor 模型通常也是 3 次，较直接路径多 1 次；若 planner 已输出完整、合法且条件具备的调用，可以直接送 broker，再让模型回答，仍为 2 次。分步骤发现/加载工具、合同失败恢复和复杂依赖会再增加相应决策轮，不能只统计第一次 HTTP 请求。

实际总等待由关键路径上的模型往返、输入处理与生成、工具 I/O、验证/持久化以及单独的审批等待相加；并行读取只减少可重叠的那一部分。提议元数据即使不多一次 API 调用，也会增加 token 与本地工作。应报告模型轮数和 token，以及 p50/p95、工具和审批分项，不能把“0 额外分类调用”写成“没有额外时延”。

| 路径 | 额外模型调用 | 时延来源与选择 |
| --- | --- | --- |
| 现有主模型调用携带小型提议、程序本地检查 | 通常 0 | 增加 schema/输出 token、校验与持久化；先测预算和 p50/p95。 |
| 已有有效回执的前置条件检查 | 0 | 本地索引/版本读取；不重复发相同观察。 |
| 条件缺证据，先观察再让主模型选择 | 通常新增 1 个决策轮 | 真实工具等待与下一次模型生成；若原任务本就需要观察，它是必要执行成本。 |
| 每条输入单独运行意图/翻译/planning agent | 通常至少 1 次串行调用 | 网络、prefill、生成和双模型分歧；不建议默认启用。 |
| 同轮完整动作计划直接经 broker 执行 | 不必多一次独立分类调用 | 仅适用于参数与条件已足够；未知依赖必须先取证，不能预填尚未产生的来源引用。 |
| SDK guardrail 内再调用模型 | 每次 guardrail 增加其调用 | 并行可以重叠部分等待，不能保证副作用之前得到结果；关键执行检查须阻塞于真实调用前。 |
| 真实审批恢复 | 本身不必增加模型调用 | 用户等待、状态保存和再次合同检查；之后是否继续模型按实际循环计数。 |

先做隔离的模型决策评估：保留当前执行政策，模拟工具回执和任务状态，让同一模型读取原话与候选描述，分别记录候选覆盖、模型工具/动作选择、条件引用、程序拒绝、真实执行模拟和恢复是否重复。58 条已见固定题只作回归，另补未参与设计的新表达。不要将“意图布尔值符合”当成某个具体 Chrome 调用能够正确执行。

第二阶段实现小型提议与任务/调用生命周期，先验证协议、预算、回执身份和上下文恢复；第三阶段再评估是否可以替换某些词法硬闸。对每个替换点列清原政策、替代的真实合同与仍由主模型承担的语义风险。以往由提示词、目录和状态一起改出的收益不能归给一个框架名字。

冻结生产代码保持不动。本方案提供可审阅接口和验证顺序，不宣称上述状态与合同已经落入 KYNXA，也不承诺现有 16 处偏差已经解决。
