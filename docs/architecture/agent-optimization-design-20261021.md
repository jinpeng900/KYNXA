## 0. 本轮实施范围与兼容基线

首轮按用户授权投入约半小时；续轮按“做完”补齐以下选定范围，只做必要短测。当时暂不提交和重启，后续用户已授权构建、替换运行版本及提交；不额外推送。沿用仓库开发 Skill、Rust/C# 职责与统一资源队列，不恢复旧后端。

已有能力是验收基线：动态工具发现与加载、长任务持续执行、插话引导、暂停恢复、原始上下文和已有输出、执行回执与未知副作用核验、即时记忆刷新、权限隔离、资源排队。优化不能用削弱这些能力换取缓存数字或存储容量。

### 已确认的补充规则

- 新增工具仍可能使工具声明之后的历史前缀失效；只增不删减少删除造成的变化，早期集中加载降低断裂发生时的前缀长度。实际收益由第2项测量，不承诺80%命中。tool.invoke保留为诊断后的实验候选，本轮不引入。
- 只有记录日期在2026-10-21或之后、且确有供应商缓存读数的样本可用于实际命中校准；更早数据仅作相对结构比较，不报告实际命中率。缺少原schema、序列化请求或分词信息的记录明确标为不完整，不用当前目录伪装历史请求。
- 指纹盐默认只存在进程内，恢复或重启建立新诊断epoch，不写检查点；跨epoch不假装连续可比。成本核算区分普通输入、缓存读取、创建及输出，避免总输入与缓存重复计费；价格按配置版本，不写死比例、TTL或64-token规则。
- 记忆修改和撤销、权限变化、工具失效与硬输入预算立即生效，不为缓存延迟。压缩与协议必要修复仍走原有正确性路径。
- 原第5.1节问答各截前2000字、第5.2节按中文/拉丁固定块长、第6.4节仅凭参数不在用户原话中就弹审批，均不原样采用。
- 回放只能估计前缀复用与费用潜力，不能替代工具准确率和任务效果检查。视觉验证不要求每次微调都渲染固定四图，也不将图片哈希投递当成审美质量证明。

离线回放开发工具已实现显式JSONL副本输入、真实计量日期边界、缺失快照标记和显式价格成本估算；前缀修改成本建议只在离线输出，不参与在线调度。尚未用正式任务历史完成策略对照或供应商驻留校准，不能把结构估算当成实际命中率预测。

续轮补齐：同函数／章节内兼容小块合并、E5工具语义发现、回执关联的未证实验收项提醒、流式事件无损减量与耐久恢复、可验证经验候选和查询。离线回放新增原请求／稳定工具顺序／控制提示追加与替换的结构对照，以及按模型／协议分组的实际读数覆盖。工具冻结和`tool.invoke`均未引入；已有任务调度、压缩90%阈值和正式回执写入链路保留。

- **前缀保护：** 可选旧回执观察去重仅在真正压缩压力或已有公共检查点收尾时进行；普通执行轮次不重复投影旧历史。工具变化、记忆撤销、权限和硬预算仍即时生效。
- **工具语义发现：** E5补充原精确／词法入口，冷态立即返回原结果；后台推理走既有模型owner、查询向量缓存和资源租约。已热态最多短等60ms，超时回退，不等待新MCP连接。配置、信任或向量空间变化后废弃旧卡片。
- **小块和验收：** 不跨未知结构、函数、标题、表格、代码围栏或页面边界；E5真实token预算不变。验收提醒每8轮至多一次，内部只提示缺少当前成功回执映射的要求，不能当作最终答复、结束条件或重做成功操作的授权；普通聊天不增加这类检查调用。
- **事件与恢复：** 只合并队列中已经到达、同段同类的连续增量，不等待200ms、不丢尾字。发布SSE前确认既有TaskJournal耐久提交；取消等待保留原批次和事件ID。新流式行无损压缩并核验长度／SHA256，旧行原样可读，工具回执和终止事件不压缩。恢复按原任务／请求／回复和序号读取已提交事实，逐段对齐正式快照；无法证明前缀时保留两份原始记录及水位，不盲追加、不重做操作。
- **经验成熟：** 成功任务通过验收后，现有私有`task_events`只保存步骤模板和原回执引用；参数值全部占位，不保存可重放的旧命令、路径或凭据。查询逐项核对真实成功操作的callId、工具名和回执id／SHA256／字节数，并核对当前工具身份。默认同方案至少3个独立已验收任务、观测跨24小时才作为导航使用，30天未验证失效。该等待只限制衍生经验复用，不阻止模型继续工作；不得用夹具或旧统计激活。全局提升仍需既有明确确认流程。

经验库首版不增加模型提炼调用，不自动生成策略／陷阱长文或强化反馈权重。自动任务提示只用已成熟方案；显式`knowledge.experience`保留当前聊天旧导航的按需读取，并标明它不是已验证方案。可选经验读取失败或资源不足回退正常工具发现，不中断任务。

## 1. 原设计结论（按第0节取舍实施）

| 问题 | 本机证据 | 本方案 |
| --- | --- | --- |
| 前缀缓存频繁断裂 | 最近 10 个任务共 105 次请求：实际命中 62.6%，纯追加时的上限 87.1%；35 次断裂，其中 31 次只命中开头 1–5K token | §3 冻结工具声明、只追加、变更对齐 |
| 断在哪里看不清 | `clientMetrics.cachePolicy` 只有策略哈希 | §2.1 分段指纹 |
| 工具经验几乎为空 | 103 个工具只有 3 个有记录；内置工具以整个目录的摘要作指纹，任一描述改动就全部清零 | §2.2 按工具 schema 计身份 |
| `knowledge.experience` 永远为空 | 全仓没有写入方，真实目录为空 | §2.3 先隐藏，§4.1 做实 |
| 工具发现靠手写词表 | `search_tools` 为正则主题 + 中英词表 + 特例加分 | §4.2 E5 语义检索与能力卡 |
| 聊天消息没有向量 | 同步只做词法发布，跨语言、换说法召回不到 | §5.1 按轮次后台语义发布 |
| 小单元碎片 | 块上限 384 个 UTF-16 字符，小单元不合并 | §5.2、§5.3 |
| 任务库膨胀 | `task_events` 85 万行、551 MiB，其中流式增量约 420 MiB | §2.6 增量合并落库 |
| 截图描述误导模型 | 图片已经发给模型，描述却写"不提供视觉" | §2.4 更正描述 |

设计原则：

1. **先量后改。** 每项都有开关和对照指标，一次只变一个机制，失败结果同样记录（沿用团队既有规则）。
2. **按缓存的价格结构决定何时改前缀。** 第三方价格表显示 DeepSeek V4 的命中价约为未命中价的 1/50～1/120。在深度 d 处断一次，要按未命中价重读 L−d 个 token；删掉 Δ 个已缓存 token，之后每轮只省 Δ×命中价。所以执行中不为省 token 改前缀，所有变更攒到本来就要断的时刻一起做（§3.2）。
3. **默认不新增模型调用。** 唯一例外是经验提炼：每个成功任务最多一次便宜模型调用，可关闭。
4. **不扩大权限。** 新机制只影响排序、投影和提示；执行仍走原有审批、回执和副作用账本。

## 2. 阶段 0：度量与缺陷修复（约 1 周）

### 2.1 前缀分段指纹与断裂归因

负责人：C（`models/cache_policy.rs`），A 负责汇总。

目标：每次请求都能说清断在哪一段、损失多少 token。

设计：

- **计算位置。** 在 `cache_policy::apply` 里、`canonicalize_request` 规范化之后计算：
  - `system`：首个 system 或 instructions 内容的哈希；
  - `tools`：工具声明数组的哈希；
  - `chain`：按消息边界的链式哈希 `H_i = SHA256(salt ‖ H_{i−1} ‖ canonical(message_i))`，每条取前 8 字节，同时记下每条消息的估算 token（`protocol::estimate_tokens`）。
- **盐只在内存。** salt 为运行期随机值，只放在 `LoopState` 内存；盐和摘要链都不进入检查点、回执或正式日志。重启或新执行段显式重建比较基线，防止有人对短消息做字典反推。
- **比较与记录。** 与同一任务上一次请求的链比较，找到第一个不同点，写入 `clientMetrics.cachePolicy.prefix`：

  ```json
  {"breakAt":"none|system|tools|message","messageIndex":12,
   "retainedTokensEstimate":2944,"lostTokensEstimate":56402,"chainLength":41}
  ```

  回执里只存比较结论，不存链本身和正文。
- **汇总。** `usage_summary` 的 `prefixDiagnostics` 按 `breakAt` 计数，保留覆盖和不完整数量，并汇总估算损失的 token；不混入供应商实际 `cacheHitRate`。
- **区分责任方。** 实际命中（供应商回执）与预期命中（链比较）同时保留：
  - 两者都低：是我们改了前缀；
  - 只有实际低：在供应商侧，比如缓存未建好、被淘汰、尽力而为未命中。

开销：每次请求做一次线性哈希，几百条消息不到 1 ms；回执增加约 200 字节。

验收：用 §3.4 回放今天的 10 个任务，至少 95% 的断裂能归到具体段；生产环境开销低于 1 ms/请求。

### 2.2 工具经验指纹修复

负责人：D（`tools/gateway_tool_memory.rs`、`storage/tool_memory.rs`）。

**根因。**
- `builtins()` 用整个内置目录的摘要作为 `builtin` 来源指纹；`replace_catalog` 只有在 `entry.fingerprint == fingerprint && same_schema` 时才保留经验。
- 所以任何一个内置工具改了描述，目录指纹就变，全部内置工具的经验都归零。
- 开发期目录改动频繁，真实数据里 103 个工具只剩 3 个有记录（都在最近一次启动之后）。
- 工具调用本身是按设计记录的：`gateway_tool_batch` → `tools::gateway::execute` → `remember_outcome`。
- MCP 侧的 `server_fingerprint` 按服务计算，没有这个问题。

**修法。**
- 来源指纹继续保留，只用来判断来源是否存在。
- 是否保留经验改为按工具身份判断：`toolIdentity = SHA256(name, inputSchema, originalInputSchema, outputSchema, toolName)`，即现有 `same_schema` 比较的字段。这样只改描述不影响经验，改 schema 只清空该工具自己。
- 迁移：读取旧文件时，如果条目指纹等于旧目录摘要，就按新规则重算身份并保留经验。
- `remember_outcome` 增加跳过原因计数：范围不符、来源不符、已禁用、结果不计入。计数进入现有诊断日志，以后类似问题能直接看到。

测试：
- 改一个工具的描述：它和其他工具的经验都保留；
- 改一个工具的 schema：只清空这个工具；
- 旧文件迁移后计数不丢。

验收：一周内，被调用过的内置工具至少 90% 有经验记录。

### 2.3 `knowledge.experience` 先隐藏

负责人：D（目录、策略），E（存储）。

现状：它只读 `Retrieval/experiences/{chat}.json`；`storage.experiences.selectSave` 全仓没有调用方，真实目录为空。

### 2.6 流式增量合并落库

负责人：A（`orchestration/gateway_runtime.rs` 的事件持久化）。

现状：`emit` 把每个 `text_delta`、`reasoning_delta` 各写成一行 `task_events`，每行还带会话、请求、时间、序号等字段。真实库中：

- `reasoning_delta` 48.9 万行，274 MiB；
- `text_delta` 16.8 万行，94 MiB；
- `assistant_segment` 17.8 万行，52 MiB。

SSE 实时推送和内存回放本身已经有界，问题只在持久化这一层。

设计：

- **合并规则。** 每个 `RequestRun` 一个持久化合并器：同一段（`segmentId`）、同一类型的连续增量先在内存中拼接，满足以下任一条件就落一行：
  - 距第一个未落库增量已过 200 ms；
  - 累计达到 8 KiB；
  - 段或类型切换；
  - 遇到非增量事件、终止事件或取消。
- **落库格式。** 落库行为 `{"type":"text_delta","segmentId":…,"delta":"拼接文本","coalesced":n,"firstSequence":a,"lastSequence":b}`。`eventSequence` 仍按实时事件递增；落库行记录它覆盖的范围，按顺序回放时拼接语义不变。
- **段状态去重。** `assistant_segment` 与上一条已落库的同段 `(phase, status)` 相同时不再落库。
- **实时推送不变。** SSE 仍逐个增量推送，桌面不需要改。
- **崩溃影响。** 最多丢失最近 200 ms 内未落库的增量；恢复沿用现有的 `content_snapshot`/interrupted 流程。

预期：增量行数下降 90% 以上，任务库日增长下降约 80%。

验收：同类任务前后对比行数和字节；强杀进程后恢复内容一致；`ChatStreamReader` 回放测试通过。

## 3. 阶段 1：缓存稳定的上下文（约 2 周）

### 3.1 任务内冻结工具声明

负责人：A（编排）、C（协议）、D（工具）。

目标：执行段内工具声明数组字节不变，消除工具增减造成的断裂。

现状：
- `select_loaded_tools` 和 `trim_optional_tool` 每轮都在调整已选工具；
- `model_tool_declarations_with_order` 按 wireName 排序后发送；
- 集合一变，数组中间就多一项或少一项，后面的整段对话都失效。
- 在 c6452603 这个任务里，有 6 次断裂紧跟在工具加载、或第一次使用文档类工具之后。

设计：

1. **核心集。** 执行段开始时一次确定，包括：
   - 固定入口：`tool.search`、`tool.load`、`tool.invoke`、`tool.result.read`；
   - 现有初选结果；
   - 本项目历史上的高频工具（依赖 §2.2 修复后的经验数据）。

   声明预算按窗口分档：窗口 ≥ 256K 时 16K token，64K–256K 时 8K token，小于 64K 保持现状。参照：内置 67 个工具全部声明约 1.5 万 token，按命中价算每轮成本很低。
2. **段内冻结。** 执行段内不增、不减、不改描述；`trim_optional_tool` 只在段开始时运行。
3. **段内新加载。** `tool.load` 把完整 schema（wireName、描述、参数）作为工具结果追加到尾部，并登记到新的 `LoopState.deferred_tools`（名称 → schema 哈希）。
4. **调用方式。** 新增固定工具 `tool.invoke {name, arguments}`：
   - 网关从 `deferred_tools` 查到 schema，用现有 `validate_schema` 校验；
   - 然后以真实工具名走 `gateway_tool_batch` 的原派发路径，审批、只读判定、操作账本、回执、经验都记真实名称，`tool.invoke` 只是边界上的别名；
   - 名称没加载过时，返回可纠正的错误，提示先 `tool.load`。
5. **换段时调整。** 压缩或执行段切换时本来就要重建缓存。这时把段内经 `tool.invoke` 用过的工具升为原生声明，长期没用的移出。
6. **Anthropic 端点。** 以后可由 C 评估官方的延迟加载工具来替代第 4 步；本方案不发送未经适配的扩展字段。
7. **系统提示。** 在稳定段增加一条说明：已加载但未原生声明的工具，通过 `tool.invoke` 调用。

开关：`KYNXA_TOOL_PLANE=frozen|dynamic`，默认 dynamic，A/B 通过后再切换。

风险：经调度器调用时，参数准确率可能略低于原生声明。对策：高频工具都放进核心集原生声明；A/B 期间观察参数校验失败率。

验收：
- 长任务命中率 ≥ 80%，工具相关的断裂接近 0；
- 在 `tool-ambiguity-holdout` 和真实任务上，参数错误率、错选工具率与基线的差距不超过 1 个百分点。

### 3.2 只追加与变更对齐

负责人：A、C。

**原则。** 设命中价与未命中价之比为 r。在深度 d 处断一次，要多付 (L−d)×(1−r) 个未命中 token；删掉 Δ 个已缓存 token，之后每轮只省 Δ×r。

举例（单位：等价未命中 token，r=1/50）：删掉 2 万 token 的旧工具输出，之后还有 30 轮，断点之后有 8 万 token。
- 能省：2 万×30×1/50 = 1.2 万；
- 要多付：8 万×0.98 ≈ 7.8 万。

不划算。结论：执行中不为省 token 改前缀，变更集中在本来就要断的时刻一起提交。

**规则。**

- **R1 控制提示只追加。** `completionReviewNotice` 这类提示，现在是先 `clear_context_notice` 再重新加，会改动中段历史。改为追加一条带 id 的新提示，并注明"取代 #id"；旧提示留到下一次压缩时清理。
- **R2 记忆。** 新增或修改的记忆先作为尾部观察追加，压缩时再并入系统段。撤销和删除仍立即生效（隐私优先，接受一次断裂）。
- **R3 工具。** 见 §3.1。
- **R4 历史重投影。** 执行中不重新投影旧轮次，只在压缩时做。c6452603 里有 4 次断裂发生在历史变短的时候。
- **R5 对齐点**，即"本来就要断"的时刻：
  1. 压缩触发（保持 0.9×输入上限，不改）；
  2. 空闲超过供应商缓存有效期后的第一次请求（DeepSeek 为小时级、OpenAI 为分钟级，按 C 维护的供应商表）；
  3. 权限、挂载或模型路由发生变化。

**数据结构。**
- `LoopState.pending_mutations: Vec<{kind, createdRound, reason, estimatedDeltaTokens}>`。
- 每轮请求前由新增的 `MutationPlanner` 判断是否在本轮提交：只有遇到对齐点、隐私类变更或超过硬上限时才提交，并在 §2.1 的诊断里记下 `breakAt` 和原因。

**验收。**
- 每 100 次请求的断裂不超过 5 次（今天是 33 次）；
- 断裂原因里"非对齐点"占比不超过 10%。

### 3.3 压缩时机不变，内容一次做完

负责人：C。

触发保持 0.9×输入上限，阈值和目标值都不改。只要求在这一次压缩里，把 §3.2 积攒的变更一起提交：
- 工具输出改成摘录；
- 旧轮次省略或摘要；
- 工具面重新规划；
- 记忆并入系统段；
- 清理已被取代的控制提示。

这样一次压缩只带来一次全量未命中。现有"摘要请求复用稳定前缀"的实现保持不变。

### 3.4 缓存反事实回放器（开发工具）

负责人：A。

目标：上线前用真实历史算出每种策略的预测命中率，不花 API 费用。

设计：

- **输入。** 从运行目录拷出来的数据目录（不读运行中的数据），加上任务 id 列表。
- **重建。** 用 `ModelTranscript.rounds[].contextBefore`、检查点和已保存的工具结果，经同一套投影代码重建每次请求的前缀。可切换的策略：工具面（dynamic/frozen）、控制提示（替换/追加）、记忆（立即/对齐）。
- **预测命中。** 与上一次请求的最长公共前缀 token 数，按 64 token 向下取整（DeepSeek 回执里的命中值都是 64 的倍数）。
- **校准。** 先在 10-21 之后有真实缓存读数的任务上，用当前策略做预测，与实际命中比较。误差不超过 5 个百分点后，才用它比较新策略。
- **形式。** 放在 `apps/agent-core/src/bin/` 下的开发二进制，或带环境变量开关的 `#[ignore]` 测试，不进安装包。

输出：每个任务的请求数、预测命中率、断裂原因分布。

## 4. 阶段 2：学习闭环与工具发现（约 3 周）

### 4.1 可验证经验库

负责人：E（存储、路径与迁移）、A（编排）、D（工具）。

目标：同类任务重复做时越来越快、越来越稳；每条经验都有证据，也会过期。

存储：`Data/Agent/experiences.sqlite`，路径经统一路径模块解析。

| 字段 | 说明 |
| --- | --- |
| `id`、`kind` | procedure（步骤模板）、strategy（策略）、pitfall（坑） |
| `scope` | work（默认）、chat、user（需用户确认） |
| `trigger`、`triggerVector` | 任务目标的规范化文本和 E5 向量 |
| `steps` | 工具名 + 归一化参数模板，路径和文件名替换为占位符 |
| `preconditions` | 适用条件：工具身份（§2.2）、MCP 服务指纹（`server_fingerprint`）、应用路径和版本、文件是否存在 |
| `evidence` | 来源任务 id、回执引用、验收结果 |
| `counters` | `reused`、`helpful`、`harmful`、`lastValidatedAt` |
| `state` | candidate、active、retired |

**生成（任务结束时）。**

1. **步骤模板（procedure）。** 只对通过验收、且有有效证据的任务生成：按顺序取操作账本里成功的副作用调用，确定性地归一化成模板，不需要模型。
2. **策略和坑（strategy/pitfall），可选。**
   - 用一次便宜的模型调用（如 deepseek-flash），输入是回执摘要，不含正文；
   - 按严格 JSON schema 产出不超过 3 条，代码检查每条引用的回执是否存在；
   - 失败的任务只产出 pitfall，并绑定错误码。
3. **去重。** 模板签名（工具序列 + 归一化参数）相同的条目合并计数，不重复入库。

**使用（任务开始时）。**
- 用目标文本做 E5 检索，取同范围、且适用条件全部满足的前 3 条。
- 作为尾部观察注入，不超过 600 token，标明"历史已验证做法，执行前仍需核实"。不进系统段，不破坏缓存。
- `knowledge.experience` 改为查询这个库：工具名不变，参数增加 `query`。

**反馈。**
- 注入后任务成功，且步数少于同类任务中位数：helpful+1；
- 按经验执行的那一步失败：harmful+1；
- harmful ≥ helpful+2，或适用条件连续两次不满足：转为 retired；
- 每个范围最多 2,000 条，按 `lastValidatedAt` 淘汰。

**安全。**
- 经验不授予任何权限，执行照常审批；
- user 范围的经验必须用户确认，与记忆草稿一致；
- 管理界面以后由 B 在记忆窗口里加一个"经验"页。

**依据。**
- Agentic Plan Caching：复用计划模板，成本约降 46%；
- ReasoningBank：成功和失败都提炼经验；
- ACE：逐条增量更新加计数，避免整体重写导致退化。

KYNXA 的不同之处：只有带回执、通过验收的经验才能晋升；复用前先校验适用条件；工具或服务指纹变了就失效。

**验收。**
- 10 类重复任务各跑 3 次：第 2、3 次的模型请求数下降至少 30%，工具调用下降至少 25%，成功率不下降；
- harmful 的占比低于 10%。

### 4.2 语义工具检索、能力卡与定向预连接

负责人：D。

**能力卡。**

### 5.2 小单元合并与按文字类型设块大小

- **版本。** `chunkerVersion` 升为 `structured-units-v2`，依靠现有派生签名逐步重建，由后台作业重新嵌入。

验收：SciFact nDCG@10 不低于 0.666（现为 0.676）；中文本地集 Recall@10 不下降；平均片段数下降。

### 6.1 只复述未证实的验收项

负责人：A（`orchestration/gateway_loop.rs`）。

- **计算。** 每轮请求前算出未证实项，即 `acceptance_requirements` 中还没有有效证据的项（复用 `task_evidence`、`unproven_requirements`）。
- **追加时机。** 集合发生变化时，或者没变但连续 8 轮仍不为空时，作为运行观测在尾部追加一条，不超过 300 token，例如："未证实：requirement-2 …；已证实：requirement-1（证据 call-…）"。内容相同时不重复追加。
- **对缓存的影响。** 只追加、不改历史，不影响缓存。

依据：目标漂移研究（上下文越长越容易偏离原目标）、Manus 的 todo 复述。不同点是这里的内容由回执决定，不靠模型自报。

验收：完成核对的一次通过率提高、重新核对的次数下降，并且不增加模型调用。

### 6.2 视觉验证流程（Blender 等）

负责人：A、D，做成官方 Skill。

图片链路已经通了，截图和渲染图都会作为图片发给模型并按哈希核对。缺的是一套验证做法：

1. 每次修改后，渲染固定的 3 个视角和最终镜头（用 Blender 命令行或 MCP），预览图缩到长边 ≤ 1024 px。
2. 用 `artifact.open` 打开，让模型看到图片；再与上一版做成对比较，问"哪一版更符合要求，逐条说明差异"。
3. 视觉类需求必须有本轮新图的视觉回读（用现有的 `requiresVisualReadback` 检查）。
4. 每轮最多 4 张新图；旧图等到压缩时再换成文字观察（按 §3.2 对齐）。

整套做法封装为官方 Skill `blender-visual-check`，不改核心代码。

依据：
- MLLM-as-a-Judge：成对比较比单独打分更可靠；
- BlenderGym：推理时多做验证，效果提升明显。

### 6.3 流式提前派发只读调用

负责人：C（流解码）、A（编排）。

现状：`gateway_tool_batch` 要等模型一步完全结束，才并行执行相邻的只读调用（`Prefetched`/`PrefetchOutcome`）。

设计：

- **C 侧（流解码）。** 某个工具调用的参数 JSON 闭合时（下一个调用开始，或协议给出结束标记），回调编排层。
- **A 侧（派发判断）。** 同时满足以下条件就立即派发，结果放进现有的 `Prefetched` 表，仍按原调用顺序结算：
  - `policy::is_read_only_call` 为真；
  - 不需要审批；
  - 属于可并发的资源（复用 `plan_with_catalog` 的规则）。
- **失败处理。** 流失败或这一步被丢弃时，已派发的只读结果标为未使用，不写入模型历史；因为是只读调用，没有副作用需要撤销。
- **排除项。** 写操作、浏览器和终端会话、未知的 MCP 工具一律不提前派发。

依据：PASTE 用模式预测做投机执行，任务时间降约 43–48%。本设计不做预测，只是提前执行，风险低。

验收：含 2 个及以上只读调用的轮次，端到端时延中位数下降；回执顺序与现有测试保持一致。

### 6.4 参数来源检查（防提示注入）

负责人：D（派发前检查）。

- **范围。** 只针对高风险工具：`terminal.host.run`、`terminal.workspace.run/write`、`filesystem.delete`、浏览器表单提交、`computer.type`，以及非只读的 MCP 工具。
- **抽取。** 从参数里抽取关键字面量：URL、Windows 路径、整条命令、邮箱，长度至少 12 个字符。
- **判定。** 某个字面量只出现在本任务的不可信结果里（`web.fetch`、`web.search`、浏览器、MCP、下载文件的内容），而从未出现在用户消息中，就走现有的行内审批卡，并说明"该参数来自外部内容（来源：…）"。
- **不拦的情况。** 用户原话里本来就有的内容不拦；只读工具不拦。

依据：CaMeL 把控制流和数据流分开。这里只做最轻量的数据来源核对，复用已有回执。

验收：注入样例集拦截率 ≥ 90%；正常任务误拦率 < 1%。

### 6.5 空闲时计算

负责人：A、B。

- **触发。** 桌面检测到空闲（`GetLastInputInfo` ≥ 10 分钟且接通电源）后通知网关；用户一有输入就立即停止。
- **任务队列。** 每项都经资源服务准入、可以随时取消：
  - 复核经验的适用条件；
  - 刷新已信任 MCP 服务的能力卡；
  - 处理积压的消息向量；
  - 块版本升级后重新嵌入；
  - 对任务库执行 `ANALYZE`，碎片率高时再 `VACUUM`。

依据：Sleep-time Compute。

## 7. 指标与验证

| 指标 | 现在 | 目标 |
| --- | --- | --- |
| 长任务缓存命中率 | 62.6% | ≥ 80% |
| 每 100 次请求的断裂 | 33 | ≤ 5 |
| 输入费用（相对） | 1 | 约 0.45–0.55 |
| 被调用过且有经验记录的内置工具 | 3/103 | ≥ 90% |
| 任务事件日增长 | 约 90 MiB | ≤ 20 MiB |
| 聊天"换说法"Recall@10 | 基本为 0 | ≥ 70% |
| 中文工具检索 top-1 | 待测 | ≥ 85% |
| 重复任务第 2、3 次的模型请求数 | 基线 | −30% |

费用估算：输入费用 ∝ 未命中占比 + 命中占比×r。r=1/50 时，命中率从 62.6% 提到 80%，费用降到原来的约 56%；提到 85%，降到约 43%。

验证顺序：
1. 先用 §3.4 回放器在真实历史上算出预测值；
2. 再用环境开关做 A/B；
3. 一次只变一个机制，失败结果同样记录。

## 8. 不做的事

- **不改压缩阈值。** 保持 0.9。
- **不冻结能力。** 只冻结声明的位置。
- **检索不加花样。** 不加统一检索路由，不做 HyDE，也不重新引入神经重排：SciFact 上 BGE 让 nDCG 降 1.2 个百分点、MRR 降 2.2 个百分点。
- **不做本地视觉旁路。** 主模型带视觉，图片链路已经通了。
- **不越权预连接。** 未信任、或用户没有点名的 MCP 服务不提前连接。
- **经验与记忆分开。** 两者不自动互转；经验不授予任何权限。

## 10. 2026-10-22 补充：DeepSeek 搜索与通用工具变化投影

**DeepSeek 搜索（内置备用来源）。** `tools/gateway_deepseek_search.rs`。已保存官方 DeepSeek 连接（`https://api.deepseek.com`，含 `/v1`）且有密钥时自动启用；自动模式下排在全部已配置搜索来源之后，只有前面的来源失败、限流、冷却或额度耗尽才会调用。显式选择其他来源时不加入；兼容网关和代理的密钥不会发往 DeepSeek。查询超过 128 字符时截取前部；结果保留摘要、站点和来源日期。工具运行时只记录模型配置目录，按需读取密钥，配置、缓存键和回执都不含密钥。真实接口探测返回 5 条结果。

**通用工具变化投影。** `models/tool_updates.rs` 与供应商无关：循环照旧选择工具，只在具备能力的路线上改写发出的请求体。序列开始时的工具保持在前，之后新增的工具以 `defer_loading` 追加，并在其首次出现的轮次后插入 `tool_addition` 更新块；历史被改写、定义变化或位置不合法时重新开始序列，按原样发送。纯文字轮次不使用也不结束序列。当前登记的能力只有 DeepSeek Messages 路线上的 deepseek-flash（仅新增，不支持移除）。

**DeepSeek Messages 路线（默认对 deepseek-flash 开启）。** `models/provider_routes.rs`。默认只有官方 DeepSeek 连接的 deepseek-flash 改道；`KYNXA_DEEPSEEK_MESSAGES_ROUTE=0` 恢复原路线，`=1` 时 deepseek-v4-pro 也改道。改道在本次运行开始时进行，走 `https://api.deepseek.com/anthropic`；保存的连接、密钥和模型名不变，路线在一次运行内固定，摘要请求同路。官方窗口识别扩展到该路径，压缩时机不变。Messages 协议发送前去掉空内容消息（DeepSeek 拒绝空消息），其他协议不变。

**真实 API 验证（deepseek-flash，隔离数据）。** 同一"写文件—联网搜索—追加—读回"任务：旧路线命中 34%～64%（多次断在工具声明），新路线 71%～75%，加载新工具后每轮都命中整段前缀。同一聊天先旧路线后新路线可接着完成任务和追问；新路线上任务进行中插话仍接回同一任务（19 次请求，命中 86%）。收尾核对轮两条路线都会断缓存：原因是 `tool_choice` 从 auto 变为 none 或去掉工具；保留工具并禁止调用的尝试经抓包确认无收益，已撤回，保持原行为。

**未覆盖。** 桌面界面未改动、未做界面验证；Anthropic 与 OpenAI 的投影翻译尚未登记；deepseek-v4-pro 的工具变化能力未核验，暂按重建处理；开关默认关闭，长期使用的费用与稳定性需更多真实任务。
