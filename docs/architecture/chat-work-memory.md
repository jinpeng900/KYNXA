# 聊天与工作记忆

本轮以现有项目作为“工作”，不另建 Work/Run/Task 身份。正式聊天记录、已确认记忆和本次模型上下文分开管理，稳定 ID 不依赖服务商、模型名称或关联文件夹位置。

## 文件结构

以下为用户选择的 Data 根目录。机器上的实际位置由设置决定，不写死在代码中。

```text
Data/
├─ settings.json                        用户设置、布局版本与存储身份
├─ catalog.json                         项目/聊天归属、标题、排序、归档及删除标记
├─ Desktop/                             界面偏好、模型选择、内置工作文件夹
├─ Models/
│  └─ connections.json                  连接、密钥、模型 ID、上下文窗口配置
├─ Memory/
│  └─ entries.json                      已确认的用户全局记忆
├─ Projects/
│  └─ 项目ID/
│     ├─ project.json                   由 catalog 生成的项目清单
│     ├─ Memory/
│     │  └─ entries.json                该工作的共享记忆
│     └─ Sessions/
│        └─ 聊天ID/
│           ├─ events.jsonl             完整正式消息事件
│           ├─ context.json             本聊天可重建的旧对话摘录
│           ├─ Memory/
│           │  └─ entries.json          本聊天独有的确认记忆
│           └─ attachments/             本聊天附件
├─ Chats/
│  └─ 聊天ID/
│     ├─ events.jsonl
│     ├─ context.json
│     ├─ Memory/
│     │  └─ entries.json
│     └─ attachments/
├─ Index/
│  └─ search.sqlite                     可重建的项目/聊天元数据索引
├─ Trash/
│  └─ 聊天ID/                           删除后移入的完整聊天目录，供撤销恢复
└─ Backups/                             迁移备份
```

目录自动初始化。`entries.json` 在首次保存该范围记忆时创建，`context.json` 在需要压缩请求历史时创建；没有发送内容的聊天草稿不成为正式会话。坏 JSON 摘录恢复时，同目录会留下 `context.corrupt-UUID.json` 原字节诊断副本。关联的外部工作文件夹保留项目文件，聊天及记忆仍归统一 Data 管理。

「不使用文件夹」的工作聊天沿用已有隐藏项目路径，但该隐藏项目不提供共享工作记忆。每个聊天只使用自己的记忆与明确指定的用户全局记忆。

## 共享关系

| 信息 | 当前聊天 | 同一工作的其他聊天 | 其他工作/普通聊天 |
|---|---|---|---|
| 完整消息历史与旧对话摘录 | 可以使用 | 不自动使用 | 不使用 |
| 聊天确认记忆 | 可以使用 | 不使用 | 不使用 |
| 工作确认记忆 | 可以使用 | 可以使用 | 不使用 |
| 用户全局确认记忆 | 可以使用 | 可以使用 | 可以使用 |

例如在工作 A 的聊天 1 发送 `记住：本项目使用 Python 3.12`，工作 A 的聊天 2 后续请求可使用该约定，但不会收到聊天 1 的整段历史。工作 B 不能使用这条工作记忆。聊天 1 发送 `聊天记住：当前实验使用样本 A` 时，只影响聊天 1。

默认只有用户消息的完整开头指令触发记忆确认：

| 指令 | 保存范围 |
|---|---|
| `记住：内容` / `记住这个：内容` | 真实、未归档项目中默认工作；其他情况下默认聊天 |
| `聊天记住：内容` | 当前聊天 |
| `项目记住：内容` / `工作记住：内容` | 当前真实、未归档工作；无工作时拒绝 |
| `全局记住：内容` | 用户全局 |

中文和英文冒号都可使用。助手回复、引用、代码块、一般对话中的“记住”字样不会自动提取。不使用模型推断来将未经确认的事实提升为长期记忆。

每条记忆保存内容、类型（fact/preference/decision）、范围、来源聊天/用户消息、确认状态、版本和时间。更新/删除使用范围文件的 `expectedRevision` 做冲突检查。单范围最多 1000 个活动条目，单条最多 4000 字符，文件最多 8 MiB；超限明确失败并保留原文件。来源撤销清单同样受文件容量约束，不静默淘汰旧撤销记录。

来源聊天归档时，已确认记忆仍有效。删除来源聊天暂停使用其消息来源记忆，撤销删除恢复；移出原工作后不再向原工作提供该来源记忆。聊天独有记忆随整个会话目录移动。手动确认条目独立于来源消息的存活。删除明确记忆会保存来源撤销标记，原请求重试不能将删除的记忆重新创建。目标工作归档后，不注入其工作共享记忆。

## 请求上下文与恢复

`events.jsonl` 始终保留完整正式记录；本次请求投影不截断源日志。当前用户输入完整保留，历史按 `ReplyTo` 选择完整成功问答，排除失败、中断尝试及可见思考内容。切换模型、重启应用或迁移 Data 不改变聊天身份及确认记忆。

每个连接可配置 `contextWindowTokens`（2048–2000000），默认 8192；1M 为 1000000。窗口须与实际模型及服务端启动配置匹配。算法使用保守字符估算，并预留输出与安全余量，不能替代供应商 tokenizer。默认输出预留 2048 tokens；小窗口按比例降低。当前输入单独超过可用预算时返回 `CONTEXT_INPUT_TOO_LARGE`，原消息和失败状态仍保存，不调用上游。

上下文在预算内加入已确认记忆，优先保留短条目全文，长条目必要时使用明确标注的首尾原文摘录。预算放不下的条目只从本次请求省略，不从长期记忆删除；构建器返回相关条目 ID 和诊断。当前不提供按问题的向量/相关性检索。

较早历史超预算时，`context.json` 保存确定性的原文摘录，不额外调用模型，也不是完整语义总结。覆盖轮次、来源哈希和内容都须与当前原日志一致，否则重新生成。记忆注入内容不会进入该摘录。坏 JSON 在备份成功后移除并重建；未来版本、链接路径及真实 I/O 故障仍拒绝覆盖。长期记忆损坏则保留文件并报错，不当作空记忆继续写入。

## 模块职责与接口

| 模块 | 职责 |
|---|---|
| `conversations.mjs` | 正式日志和目录事务；按稳定 ID 查询当前归属与兄弟聊天元信息 |
| `data-layout.mjs` | 补齐目录并检查版本和链接路径 |
| `memory-contracts.mjs` | 范围、来源、内容及版本校验；明确指令识别 |
| `memory-repository.mjs` | 记忆与摘录持久化、原子替换、文件队列与版本冲突保护 |
| `memory-service.mjs` | 记忆确认、来源有效性、工作隔离与可用范围查询 |
| `context.mjs` | 不修改源数据的上下文预算、轮次选择、记忆投影及摘录验证 |
| `runtime.mjs` | 发送前确认记忆/组装上下文；调用模型并保存完整或失败状态 |
| `protocols.mjs` | 三类协议的系统字段及输出预算映射 |

所有正式写入由单个网关拥有。记忆和摘录的读写先进入正式会话队列，再进入文件队列；聊天移动或删除须等待这些读写完成，避免写回旧会话目录。版本检查防止多个客户端覆盖共享记忆。这不是多个网关同时写同一 Data 的跨进程数据库事务方案。

后端提供 `/api/conversations/:chatId/relationships` 和 `/api/conversations/:chatId/memory` 查询；记忆 POST 创建、PATCH 修改、DELETE 删除，详细参数见 [模型网关说明](../../apps/model-gateway/README.md)。关系接口只返回兄弟聊天元信息。桌面通过健康协议检查拒绝复用缺少记忆/上下文能力的旧网关。

测试使用独立临时 Data 和模拟上游，覆盖共享隔离、归档/删除/撤销、来源移动、换模型、重启、真实迁移、三协议与 SSE、版本冲突、容量边界、路径链接、摘录篡改及损坏恢复。完整记忆管理 UI、模型自动学习、全文/向量检索及执行检查点留作后续功能。
