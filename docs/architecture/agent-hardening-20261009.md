## 代码职责与语言

模型协议及预算检查在 C 的 `models/`；任务恢复、上下文分配及证据装配在 A 的 `orchestration/`；MCP/Skill 生命周期在 D 的 `tools/`；FTS、引用和索引 worker 在 E 的 `data/`。仅新增三个职责明确的产品模块：`models/tool-call-validation.mjs`、`orchestration/tool-recovery.mjs`、`orchestration/retrieval/context-allocation.mjs`。没有创建只有转发作用的新框架层。

C# 只改模型流消费及检索 DTO：允许已中断进展段之后的有效最终段、兼容可选重排参数。B 的 Views、Controls、Resources、ViewModels 和 UI 状态接线没有改。公开名称、正式数据身份和现有入口兼容；新增字段保持可选。非显然行为采用英文与中文说明注释，第三方代码和许可证不改写。

## 方法依据与创新判断

- [Cursor Dynamic context discovery，2026](https://cursor.com/blog/dynamic-context-discovery)：借鉴少量目录线索、按需加载、保留历史/工具结果回读；KYNXA 使用既有服务和正式结果归属，不复制产品整体实现。
- [Sufficient Context，2025](https://research.google/pubs/sufficient-context-a-new-lens-on-retrieval-augmented-generation-systems/)：区分检索命中、上下文足够与回答正确。本次没有训练充分性分类器，也不把 `knowledge.assess` 当成逻辑蕴含证明。
- [cAST，2025](https://arxiv.org/abs/2506.15655)：支持既有结构化代码分块方向；本次保留原文、单元范围和版本回读，未重造解析器或复现论文成绩。
- [The Complexity Trap，2025](https://arxiv.org/abs/2508.21433)：支持优先收缩旧观察并保留回查的效率方向；本次沿已有配对历史压缩，没有宣称论文的成本收益属于 KYNXA。

差异主要是工程组合：Windows 桌面/宿主终端/AppContainer、两类本地检索、范围与版本绑定、动态资源及副作用回执共用一条编排链。不能据此称为原创检索算法、头部 Agent 水平或新的已验收论文方法。

## 验证与交付

测试只使用独立临时数据、模拟凭据、本机 HTTP/SSE 和合成 SDK 服务；没有调用用户付费模型或操作个人浏览器账号。重点是三协议“成功写入 → 解码失败 → 新 ID 的重复请求 → 复用真实回执 → 下一条用户消息”的完整历史链路，以及取消、未知结果和预算失效。
