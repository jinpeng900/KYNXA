# Windows native tool host

## Host terminal channel

`host_terminal_capabilities` and `host_terminal` provide explicit host CMD/PowerShell execution, separate from AppContainer. They do not require Python. The gateway owns approval and immutable request scope; the helper owns fixed shell paths, inherited host environment, output/deadline limits and Job process-tree cleanup. Normal command exit, including nonzero, has a completion receipt; interrupted effects remain unknown. See [native host terminal verification](../../tests/native-host-terminal-smoke/README.md) for the JSON-line contract, encoding limits and executable checks.

`KYNXA.ToolHost` is a .NET 10 helper with separate sandbox, desktop and host-terminal channels. `sandbox-runner.mjs` executes terminal/skill scripts inside AppContainer; `desktop-runner.mjs` reads and controls explicitly selected windows on the interactive host desktop. Desktop access is outside AppContainer and remains subject to the gateway broker's approval/scope checks. No channel elevates privileges or bypasses protected desktops/UIPI. Sandboxed terminal execution never falls back to a host shell.

Build with `dotnet build apps/tool-host/KYNXA.ToolHost.csproj`. Desktop packaging builds a self-contained helper for its runtime identifier (`win-x64`, `win-arm64`, or `win-x86`) and copies the complete output into `ToolHost` beside `model-gateway`. For a standalone self-contained build use `dotnet publish apps/tool-host/KYNXA.ToolHost.csproj -c Release -r win-x64 --self-contained true`. WindowsDesktop/UI Automation/PNG dependencies are included in that output; installed users need no Python or separate .NET runtime. Framework-dependent development builds require .NET 10 WindowsDesktop.

The helper reads one UTF-8 JSON request line from stdin. A second `cancel` line or stdin EOF cancels execution: clients keep stdin open while awaiting a result. Protocol version is `1`. Sandbox `run` emits `sandbox_started` followed by one final result/error line. Capabilities and desktop actions return one JSON line. Node stdout/stderr is returned only inside the sandbox result. The gateway never treats helper diagnostics as model thinking.

## Interactive desktop channel

`{"operation":"desktop_capabilities"}` reports `available`, `interactiveWindows`, the thirteen supported `operations`, allowed key combinations and `boundary:"host-desktop"`. Actions use `operation:"desktop"` and the following fields:

| Action | Inputs and result |
| --- | --- |
| `apps` | Known Windows GUI apps and HKCU/HKLM App Paths, at most 128 absolute executable paths; no recursive disk scan. |
| `windows` | Optional positive `processId` filter; at most 200 visible top-level windows with window ID, PID, title, process name/path, client dimensions, foreground/minimized state and `isResponding`. The filter is applied before reading titles. |
| `read` | Explicit `windowId` and matching `processId`; visible UI Automation text/elements/HTTP(S) addresses. `maxCharacters` defaults to 16,000 and is limited to 64,000; `maxElements` defaults to 200 and is limited to 1,000. `timeoutMs` defaults to 3,000, range 500–5,000. Optional `elementId` selects a returned runtime ID within that same window; optional `region:{x,y,width,height}` selects intersecting accessible elements/ranges in client physical pixels. |
| `screenshot` | Explicit window/PID; selected client only, PNG `data` base64 with `mimeType`, physical `width`/`height`. Optional `crop:{x,y,width,height}` retains original pixels without scaling. Maximum 16M source pixels, 8,192 per dimension and 4 MiB PNG. No whole-desktop fallback. |
| `launch` | Absolute local GUI `.exe` `appPath` plus string-array `args`, through `CreateProcessW` with handle inheritance disabled and correct Windows argument quoting. Background defaults to true: `SW_SHOWNOACTIVATE` and a bounded 1,500 ms startup observation place only that PID's actual windows behind the selected foreground window. `background:false` explicitly requests normal startup. The receipt reports observed placement/focus, not a permanent guarantee; the new PID must still be matched to a discovered window. Existing applications are never closed or attributed to a delegated launch. |
| `window` | Explicit window/PID; `mode` resize/maximize/minimize/restore. Resize requires client `width`,`height` in 64–8,192 physical pixels and a restored window. Background targets stay behind the selected foreground window; operations on the currently selected target do not demote it. The receipt reports actual dimensions/state, placement and foreground preservation. Restore returns to normal size, including from a minimized maximized window. |
| `activate` | Explicit window/PID; restores a minimized target and requests foreground activation. Windows may deny focus; no focus restrictions are bypassed. |
| `move`, `click` | Explicit foreground window/PID plus client `x`,`y`; click `button` is left/right/middle. |
| `scroll` | Foreground target and client point, nonzero `delta` within ±1,200, `direction` vertical/horizontal. |
| `drag` | Foreground target, client start `x`,`y` and destination `endX`,`endY`; bounded left-button path. |
| `type` | Foreground target plus `text`, 1–4,000 UTF-16 characters without NUL; Unicode SendInput, not clipboard paste. |
| `key` | Foreground target plus an enumerated `key`, e.g. `ENTER`, `CTRL+A`, `CTRL+L`, `SHIFT+TAB`, `CTRL+PLUS`, `CTRL+MINUS`, `CTRL+0`; capabilities is the authoritative list. |

Every successful action includes `protocolVersion:1`, `boundary:"host-desktop"`, `action` and `completed:true`. Window identities use decimal HWND strings plus a matching process ID. Input checks the target, foreground, integrity level and unobscured client coordinates before each batch. Held physical modifiers/buttons or requested keys cause refusal. The sender records only the prefix actually accepted by SendInput, then releases its own delivered key/button presses after success, cancellation or failure. Incomplete release reports `DESKTOP_INPUT_RELEASE_FAILED`; failures report `partial` and `deliveredInputEvents` instead of successful completion.

`DesktopForegroundPlacement` owns the shared app/console placement policy. Placement uses `SWP_NOACTIVATE` and a nonblocking Z-order request; windows remain restored and can be captured with the existing target-only `PrintWindow` channel even while obscured. If the known target activates during startup, ordinary `SetForegroundWindow` requests restoration of the last unrelated foreground identity. A user selecting another application updates that identity; no `AttachThreadInput`, synthetic input or foreground-lock bypass is used. `backgroundPlacementConfirmed`, `foregroundPreserved`, `focusRestoreAttempted` and `focusRestoreSucceeded` report actual observations. Applications that override focus later, delegate to a different existing process, use topmost/owned windows, or start after the bounded observation can still require explicit window discovery. Background launch does not claim permanent focus suppression. Physical mouse/keyboard input still requires explicit activation; DOM/UIA reading and target screenshots do not.

Windows Chromium can suspend the renderer/accessibility tree of a completely covered browser window, even if the window is not minimized. Background Chrome/Edge automation therefore uses the documented `--disable-backgrounding-occluded-windows` option in the approved launch arguments; the native helper never silently inserts or rewrites arguments. A newly launched browser with this option retains document text and rendered target screenshots behind KYNXA. An already running browser may ignore new launch switches, so existing-profile attachment still depends on the browser's state and provider capabilities; prefer the configured DOM/browser connection for web work. See [Google's tooling flag guidance](https://github.com/GoogleChrome/chrome-launcher/blob/main/docs/chrome-flags-for-tools.md) and the [Chromium ChromeDriver change](https://chromium.googlesource.com/chromium/src/+/23902d9051098fbc6a3a669fc0988c6899f38b65%5E%21/).

Explicit visible host terminals use the same no-activate startup hint and verified console-window placement before command execution. Default captured host commands retain `CREATE_NO_WINDOW`; neither mode renders a terminal in the right sidebar. Real console input/output, command receipts, bounded snapshots, cancellation and Job cleanup remain unchanged.

GUI launch accepts PE GUI executables, refuses shells/interpreters/terminal launchers (including renamed executables with a blocked original filename), and blocks known command/script-evaluation arguments. It cannot be used as a terminal sandbox replacement. Read/screenshot also reject higher-integrity processes. Reads first perform a bounded `WM_NULL` response check and reject `DESKTOP_NOT_RESPONDING`; a stalled UIA provider returns `DESKTOP_READ_TIMEOUT` within the requested deadline. Other operations retain an 18-second worker limit. The gateway additionally supervises each separate helper process, whose background UIA thread cannot keep it alive after a timeout receipt.

`read` returns `source:"uia-visible"`: accessible content that intersects the selected client/region, not an exact text clipping operation, full browser DOM, offscreen page or document export. Password controls retain only `isPassword`, location, control type and bounded locator metadata; their Name, Value and TextPattern are never read. They can receive approved foreground `type` input. UIA providers may omit content. Chromium accessibility initialization can be asynchronous, so a first read may expose browser chrome before document content. Unsupported, minimized, protected or locked targets fail explicitly. Native browser smoke verifies real Edge and Chrome with fresh temporary profiles, forced renderer accessibility and a loopback page; it never reads a user's browser profile.

Native verification commands and artifact rules are in [the desktop smoke README](../../tests/native-desktop-smoke/README.md). Microsoft references: [UIA threading](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-threading), [SendInput/UIPI](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput), [PrintWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-printwindow).

## Terminal and skill sandbox channel

Only command names `node`, `node.exe`, `cmd` and `cmd.exe` are accepted. The gateway supplies its own `process.execPath`; cmd is copied from `Environment.SystemDirectory`. Tool arguments cannot choose an executable path. Debugger flags are rejected. Node runs with `--preserve-symlinks` and `--preserve-symlinks-main` so loading a snapshot script does not require probing inaccessible host ancestor directories. Use `node --test --test-isolation=none fixture.test.cjs`: default process-isolated Node test IPC is incompatible with this AppContainer. Ordinary child processes inherit the AppContainer token and remain subject to the same job.

For `skill.run`, the gateway supplies an approved `skill` package separately from the writable workspace: `{root, script, files:[{path,size,sha256}]}`. `SkillSnapshot.cs` accepts only the selected manifest, at most 128 files, 2 MiB per file and 8 MiB total. It rejects ambiguous paths, links, hard links and sensitive filenames, checks the opened source handle, and verifies every copied file's SHA-256 before starting Node. The package is copied to `.sandbox-skill` with read-only AppContainer access; whole-package rename and file writes are denied. The helper selects the manifest's js/mjs/cjs entry point itself and treats the remaining arguments as script arguments. No dependency installation, Python/Bash/PowerShell runner or host execution is added.

Protocol `1` remains compatible with ordinary terminal requests. Skill execution requires the explicit capability `skillExecution:{manifestVersion:1,readOnlyPackage:true,hashChecked:true}` and a matching completion receipt with `script`, `fileCount` and `scriptSha256`. The gateway checks this contract before approval and after execution, so an older helper that ignores unknown request fields cannot report a successful skill run. See [the native skill smoke](../../tests/sandbox-smoke/README.md) for actual package write/rename denial and stale-manifest checks.

cmd is restricted compatibility, with arguments exactly `['/d', '/c', 'command text']`. The helper forces `/d /u /s /c`: AutoRun and interactive input are disabled, builtin output uses Unicode, and command text remains inside AppContainer. Actual smoke covers `echo`, `type`, output redirection, and a cmd-created Node child. `dir` can be denied when it requests host volume/root metadata; use `filesystem.list/search` for listing. No host ACL is relaxed and no shared DOS drive mapping is created. Child programs can emit a different encoding than `/u` builtins, so avoid mixing Unicode builtin and non-Unicode program output in one command.

Each run copies at most 512 files, 2,048 entries, 32 MiB total and 4 MiB per file, to `%TEMP%/kynxa-tool-sandbox/<random>/workspace`. Nesting is limited to 32 levels. Copying excludes links/reparse points and hard-linked files, configured application Data roots, `Data`, `Models`, `Memory`, chat/index/backup directories, credential/configuration directories, `.git`, dependency/build directories, common credential filenames, `.env*`, private-key/certificate files, settings and transcript logs. Open file handles are checked against the allowed source root before copying. These exclusions cannot recognize arbitrary credentials embedded in otherwise ordinary source files; choose the authorized workspace accordingly. The original workspace ACL and files are unchanged.

The service may pass `trustedManagedWorkspace: true` only for a catalog-owned default project folder or a conversation-owned managed workspace. It is absent from model tool parameters. The helper accepts the exact shapes `<excluded Data root>/Desktop/Projects/<GUID>` and `<configured model home>/Workspaces/<GUID>` (the default model home is Data/Models). A custom model-home name requires the explicit trusted `conversationWorkspaceHome` role field and an exact matching excluded root; an arbitrary excluded folder cannot acquire that role. Only strict ancestors of the selected work folder are bypassed. Sensitive child directories, exclusions inside the workspace and `.workspace-owner.json` still stay out of the snapshot. Data/Chats and adjacent conversation workspaces do not obtain access.

The stage receives a protected ACL for the current user, SYSTEM, administrators and the unique AppContainer SID, plus a low-integrity label. No network capability is granted. A child is created suspended, assigned to a Job Object, and its `TokenIsAppContainer` value is checked before resume. The job permits at most 16 processes, 256 MiB committed memory per process, and 768 MiB per job. Combined stdout/stderr is limited to 256 KiB; exceeding it terminates the job. Timeouts are 100–120,000 ms. Completion, timeout and cancellation terminate all descendants, and successful results verify the job has zero active processes. The non-inherited job handle has `KILL_ON_JOB_CLOSE`, so terminating the helper also ends its children.

Successful stages are retained during the tool turn for explicit inspection, without writing files back. `SandboxRunner.cleanup(result.stagingDirectory)` removes only a run returned by that runner; `cleanupAll()` handles remaining owned copies on service close. The broker releases stages when a turn completes. Graceful cancellation/failure removes its stage and profile. Abrupt OS/process termination can leave a uniquely named profile and temporary copy; job cleanup still terminates execution. Disk growth created by the script is not an OS disk quota, and AppContainer is not a VM: do not describe either as provided. PowerShell/Python, arbitrary top-level executables, external networks and remote MCP processes are not enabled by the terminal/skill sandbox channel.

Official design references: [AppContainer launch](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer), [mandatory integrity control](https://learn.microsoft.com/en-us/windows/win32/secauthz/mandatory-integrity-control), [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).
